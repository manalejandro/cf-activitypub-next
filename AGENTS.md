# This is NOT the Next.js toolchain you know

The app runs on **vinext** (Cloudflare's reimplementation of the Next.js API on Vite), not on the Next.js compiler: `vite dev` / `vite build` / `vinext-cloudflare deploy` replace `next dev` / `next build` / OpenNext, and the app executes inside workerd in dev and production. Keep using the Next.js 16 public API (`next/*` imports, App Router conventions), but read `npx vinext check` / https://vinext.dev/docs/reference/differences before assuming an internal or a newer experimental feature behaves like Next.js.

# CF ActivityPub — Agent Instructions

A Mastodon-compatible ActivityPub server running entirely on Cloudflare Workers via **Next.js 16 App Router on vinext + @vinext/cloudflare**. There is no Node.js server, no Docker, no database server — everything is a Cloudflare binding. This file is the working contract for anyone (human or AI) changing this repo.

## Ground rules

- **Next.js 16 API on vinext** (see the warning block above). Route handlers receive `{ params }` as a `Promise` and must `await` it. Do not assume your training data's API; vinext shims the Next.js 16 surface, and the compatibility report (`npx vinext check`) is the source of truth for what is implemented.
- **No `next` dependency**: the toolchain is vinext, so the public `next/*` modules are resolved to vinext's own shims at build time (`vinext/dist/shims/public-shim-map.json`), the type declarations come from `vinext/types` (referenced by the vinext-generated `next-env.d.ts` — never edit that file by hand), and the **test projects apply the same mapping in `vitest.config.mts`** (`NEXT_SHIMS`): a new `next/*` import has to be added there or the tests fail to resolve it. The ESLint config (`eslint.config.mjs`) inlines the 112 rules of the old `eslint-config-next` `core-web-vitals` + `typescript` presets, because that package requires the Next compiler; the parser is `typescript-eslint`'s. `npx vinext check` reports 97% with no issues (`images: { unoptimized: true }` is the expected partial).
- **`src/worker.ts` is excluded from the main tsconfig** (it imports the vinext app handler), so plain `npx tsc --noEmit` never checks it — a missing import there once reached production (`ReferenceError: mediaCacheLimitsFrom is not defined`). Validate it with `npx tsc -p tsconfig.worker.json --noEmit`.
- **Cloudflare Workers runtime.** Never use Node-only globals in runtime code (`nodejs_compat` is enabled, but stay portable). Bindings are read with `import { env } from "cloudflare:workers"` — never `process.env`.
- **No secrets in git.** `wrangler.toml` holds public vars, bindings and resource IDs only. Secrets go through `wrangler secret put`. **`.env.example` is the reference of every environment variable with its default**: copy it to `.env` (gitignored; `.dev.vars` is accepted as a second local name and takes precedence when both exist) to change anything in development **and at deploy** — the `dotenvIntoWorkerVars` plugin (`vite.config.ts`) merges `.env` into the emitted `dist/server/wrangler.json` at the end of the build, because the Cloudflare Vite plugin only fills names `wrangler.toml`'s `[vars]` do not already define and wrangler uploads the config as it is (`GRAPH_MAX_NODES=777` deployed as `1000` otherwise). Secrets are never copied into the config (`*_SECRET`/`*_TOKEN`/`*_PRIVATE_KEY`/`*_API_KEY`/`*_PASSWORD`/`CALLS_TURN_KEY_ID` are skipped with a warning): set those with `wrangler secret put`. `npm run check:env` fails when the code reads a variable that is missing from the reference (and checks `.dev.vars.example` too when present), so the list stays complete.
- **Validate before finishing:** `npx tsc --noEmit && npx tsc -p tsconfig.worker.json --noEmit && npx eslint . && npx vitest run && npm run check:env`. All must stay green. After adding/removing routes or touching `vite.config.ts`/`wrangler.toml`/`src/worker.ts`, also run `npx vite build` — the vinext build is the production gate (`next typegen` no longer exists; vinext does not generate route types).

Wrangler needs the D1 name explicitly:

```bash
npx wrangler d1 execute <db> --remote --json --command="EXPLAIN QUERY PLAN SELECT ..."
```

`--file=` is broken in this environment (`fetch failed`); always use `--command=` for one statement and `scripts/upgrade-schema.mjs` for batches/backfills.

- **API docs**: `npm run generate:openapi` (runs on predev/prebuild/prepreview/predeploy) writes `lib/api-docs/openapi.json` for the Swagger UI; `npm run check:openapi` fails when the committed spec is stale. The generator is **self-contained** (no metadata file): it scans `app/**/route.ts` and derives paths/methods, tags from the path, query params (`searchParams.get`), request bodies and the file's leading comment as description. Security is read from the handlers: everything under `/api/**/admin` is locked (administrator/moderator role), as is any handler that resolves the caller (`getAuthenticatedActor`, `getAdminRole`, manual `Bearer` parsing) and rejects a missing one (`if (!actor) return unauthorized()`, `role !== "admin"`). Endpoints that only read the viewer optionally (public timelines), login/registration endpoints and HTTP-signature inboxes stay public. Handlers that delegate (`PATCH → PUT`) or are re-exported inherit the target's guard. The heuristics read the **raw source, comments included**: a doc comment that mentions an `if (!actor) … unauthorized()` shape is classified as an auth guard, so describe the pattern without writing it literally. **Response schemas are generated from the TypeScript types** (`lib/types/index.ts` plus the declared return types of the `lib/mastodon` serializers, converted with the TypeScript compiler), and each operation is wired to the schema of the serializer it calls (arrays for `.map()`/timeline builders, per-property refs for envelope responses). `lib/__tests__/openapi.test.ts` asserts the committed file matches the source and pins the lock/public and schema matrices.

## Data layer (D1 / SQLite) — lessons learned the hard way

- **`lib/db/schema.sql` is the single source of truth.** `scripts/upgrade-schema.mjs` replays every `CREATE TABLE/INDEX IF NOT EXISTS` from it, so operators using the script alone stay current. Still add numbered `scripts/NNN-*.sql` files to document each change; update `lib/db/drop.sql` (generated, children before parents) when adding tables.
- **Measure before optimizing.** Use `EXPLAIN QUERY PLAN` against the remote DB. Confirm the plan uses the index and that `rows_read` drops. `USE TEMP B-TREE FOR ORDER BY` over tens of thousands of rows is the usual smell.
- **SQLite/D1 does not use expression indexes for `ORDER BY`**, and partial indexes whose predicate uses `IN (...)` are not matched by the planner. Don't design around them.
- **`col IN (...)` on the leading index column defeats ordered scans.** Split hot queries into one branch per value with `UNION ALL` (each branch gets its own ordered index scan) and, when the planner still prefers a range index, force it with `INDEXED BY idx_name`.
- **Home timeline boosts** (`getHomeTimeline`) must drive from `announces` through `idx_announces_created` (`INDEXED BY` + `CROSS JOIN`): left alone the planner drives from `objects` (the `visibility` OR becomes a MULTI-INDEX OR over every public object) and read ~1.5M rows / 11 s per request on cf-ap; forced, the LIMIT stops after the newest followed boosts (~600 rows / 3 ms). `actor_id` sits in the index so the followed-actors membership filter stays index-only when the user follows nobody. Profile timelines with boosts (`getActorStatuses` with `includeBoosts`, `getActorBoosts`) use `idx_announces_actor_created` (ordered scan per account, early stop; a top booster's tab went from ~16k rows / 820 ms to 40 rows / 3 ms).
- **Cron scans must early-stop or be throttled** (measured on cf-ap, per tick): `detectRepeatedSpam` groups in SQL (`GROUP BY actor_id, content HAVING COUNT(*) >= 3`, then `contentHash` merges variants) instead of loading 3000 posts and running the signal regexes in JS every 5 minutes — repetition is the only way to reach the action threshold, so per-row analysis was pure CPU; the orphan sweeps (`listOrphanMediaCache`, `cleanupOrphanPreviewCards`) select over the whole table, so the cron runs them **hourly** via KV markers (~26k and ~7k rows per run); `backfillRemoteSharedInboxes` drives from `follows` (`INDEXED BY idx_follows_target` + `CROSS JOIN`, followers branch) with `idx_actors_shared_inbox` for the other — scanning `shared_inbox IS NULL` and probing `follows` per actor read ~37k rows per tick (32k remote actors missing a shared inbox), the forced plan reads ~500.
- **Production analytics (Oct 2026) — the queries that were burning the CPU**: `objects` carried **21 indexes** (every federated insert maintained all of them); three were redundant (`idx_objects_actor_id`, `idx_objects_visibility`, `idx_objects_reply`, plus `idx_object_tags_tag_published` — a wider index in each case already leads with the same columns) and `idx_objects_card_id` is now **partial** (`WHERE card_id IS NOT NULL`: only a few percent of rows carry a card, and every consumer filters `card_id IS NOT NULL`, which the hinted repair query must keep doing or `INDEXED BY` fails). The media-cache card reset joined `objects` → `preview_cards` and the planner scanned the whole card index (**402M rows read**): a `CROSS JOIN preview_cards CROSS JOIN objects INDEXED BY idx_objects_card_id` forces the order (cache list first, then the probe) and `idx_preview_cards_image_cache` backs it. `WHERE is_local = 0 AND id IN (...)` sent the planner to `idx_actors_is_local` (a scan of every remote actor) instead of the primary key: the filter belongs in JS. A **case-insensitive `LIKE` cannot use an index**, so the hashtag autocomplete scanned `object_tags` (800k rows per call) — a lowercased prefix with `GLOB` is an index range on `(tag, published DESC, actor_id)`. Per-actor window counts (`countStatusesSince`) needed the covering `idx_objects_actor_pub_type`. And the one-shot card repair re-ran on every throttled pass while the attachment cursor was still walking (123 calls, 4.1M rows, 26% of the DB time): it now sets its own `media_cache_cards_repaired` marker once a pass finds nothing.
- **Don't `ORDER BY` a computed expression over a big table.** Denormalize and maintain on writes:
  - `objects.engagement` = favourites + reblogs + replies (kept in sync in every counter mutation; index `idx_objects_trending`).
  - `actors.last_status_at` = max public status date (maintained by `createObject`, `deleteObject`, remote upsert and the scheduled-publish cron; index `idx_actors_discoverable_active`; directory ranks by it).
  - `objects.has_link` = content mentions a link (maintained by `createObject`/`updateObject`; index `idx_objects_actor_type_link`). The Guardian patrol counted link-posts with `content LIKE '%http%'`, which read every body; the count is now index-only. Existing rows are backfilled by `upgrade-schema.mjs` (marker `backfill:objects_has_link`).
  - `idx_objects_url` backs the Like/Announce URL fallback.
- **Correlated `MAX(published)` subqueries per row are a smell** — precompute on `actors` instead.
- **D1 bind limit ≈ 100.** For long `IN` lists pass a JSON array and use `json_each(?)`.
- **List timelines** (`getListTimeline`) prefilter the (small) member set minus blocked actors/domains, then run one ordered scan per visibility (`UNION ALL` + `INDEXED BY idx_objects_vis_published`). Never join `list_accounts` with `visibility IN (...)` + correlated `NOT EXISTS`: that plan scans every public object and sorts it (~8M rows/request in production analytics).
- **Suggestions** (`getAccountSuggestions`, `/api/v2/suggestions` + Explore → Accounts): pools fill in order — friends-of-friends → local accounts → most followed on this instance → **popular in the fediverse** (`SUGGESTION_GLOBAL_MIN_FOLLOWERS` advertised followers, active in `SUGGESTION_GLOBAL_ACTIVE_DAYS`; Mastodon's `FollowRecommendation`/`AccountSuggestions::GlobalSource` is a precomputed version of this, and it is what fills the list on a small instance — a heavy remote follower exhausts the local pools, and friends-of-friends can only see the follows of **local** accounts, the only ones we store) → active local — and a **new-instances** pool (remote actors with a high advertised `followers_count`, active, whose domain has **no accepted local follow**, matched through an anti-join over the local follow domains) is interleaved every 5th slot: without a reserved share the other pools fill the list and servers nobody follows here never surface, so the federation graph stays closed. Suspended instance domains (`instance_domain_blocks`, `severity = 'suspend'`) are excluded from every pool. The pools are seeded with **instance follow recommendations** (`lib/follow-recommendations.ts`, Mastodon's `FollowRecommendation`): the cron (`setStage("suggestions")`, daily KV throttle) ranks what the **recently active** local accounts follow (`most_followed`) plus the authors of the window's most engaged public/unlisted posts (`most_interactions`, `SUM(engagement)` through `idx_objects_trending` with `INDEXED BY` and one branch per visibility — without that hint the scan reads every object of the window, 8.8 s vs 1.4 ms on cf-ap), sums `n/(1+n)` per signal like Mastodon and stores the top 300 in KV (`suggestions:follow_recommendations`, 3-day TTL); `/api/v2/suggestions` reads it and `getAccountSuggestions` applies the viewer's exclusions in one `json_each` query while keeping the ranking order. Pools **rotate daily within windows of 5 ranks** (`rotateSuggestionWindows`): the old tie-only rotation was invisible on instances whose top accounts had distinct follower counts, so the same list was suggested for days.
- **Large backfills must be batched**: single full-table `UPDATE`s hit `SQLITE_NOMEM`. Walk an id cursor and chunk statements by bytes in `upgrade-schema.mjs`; guard one-shot migrations with `instance_settings` markers.
- **Federated-history retention is opt-in** (`lib/storage-retention.ts`, cron stage `storage-retention`): by default the instance keeps every status and every processed activity it stores — that is the fediverse's memory. Two env vars bound it, both 0 (off) by default: `DB_RETENTION_DAYS` deletes remote **public/unlisted** statuses older than N days, and `DB_RETENTION_MAX_BYTES` prunes the oldest history while the database is over that size (`DB_RETENTION_PRUNE_BATCH`/`DB_RETENTION_SIZE_BATCH` keep each tick bounded, so a backlog drains over several runs). **Never pruned**: local posts, direct messages, followers-only remote posts, and remote posts a local account bookmarked or replied to (their library and their thread) — plus accounts, follows, reports and the moderation log. Deleting a status cascades like the origin deleting it (attachments, likes, boosts, bookmarks, polls, tags, notifications, the link-preview queue) and the media-cache maintenance then drops the orphaned R2 copy in the same tick; a pruned reply releases its slot in the surviving parent's `replies_count`/`engagement` through one CTE `UPDATE` (parents deleted in the same batch are excluded), while `actors.statuses_count` is deliberately untouched — it is the number the remote server advertises, never a count of what we happen to store. The batch select is `UNION ALL` per visibility with `INDEXED BY idx_objects_vis_published` (an `IN (...)` on the leading column would sort half a million rows) and its two `NOT EXISTS` guards are covering-index probes (`idx_bookmarks_object`, `idx_objects_local_reply`) — measured on cf-ap: 53 ms / 1036 rows read for a 500-row batch. The payload walk **always runs** (even with retention disabled — the admin panel shows the federated history it measures), and a pass publishes only when **both** tables have been walked end to end: a table that finishes is skipped until the pass publishes, because the first walk restarted the finished table from rowid 0 while the other was mid-scan and a pass then only completed if both windows happened to be short in the same call (never, on a busy instance — cf-ap counted 805k object rows for a 516k-row table with `bytes` still at 0). The byte budget compares against the **real file size** D1 reports in every statement's `meta.size_after`, minus what retention has freed since the file last shrank (`nextFreedBytes`): SQLite reuses deleted pages instead of shrinking, so `size - freed` is what decides whether the database will keep growing, and a runtime that reports no size falls back to a rowid-window walk of the prunable payload (`objects.raw`/`content`/`card_json` + `activities.raw`). The admin panel shows the size, the prunable payload, the last prune and a "prune now" button (`GET/POST /api/v1/admin/storage`, the manual pass audited as `storage_pruned`).
- **Never `DROP` stateful tables in the upgrade script** (`delivery_rejections` was wiped every run once — don't repeat that).
- Wrap queries in `try/catch` with a migration pointer when columns may be missing on old DBs (`last_status_at`, `quote_id`, …).
- `lib/db/index.ts` has shared SQL constants (`PUBLIC_STATUS_TYPE_SQL`) and helpers (`isAcceptedFollower`, `countActorPublicStatuses`, `deleteRemoteActorData`). Reuse them; don't inline the type list or fire raw ownership-less deletes.

## Federation rules

- **All outbound delivery goes through the queue** (`enqueueDeliveries`; fan-outs larger than 100 are chunked by count *and* byte budget, each chunk is retried and only a persistently failing chunk falls back to direct delivery — never the whole recipient list). `deliverToInbox` is only reachable from `lib/activitypub/queue.ts` (fallback when no binding/`sendBatch` throws) and the worker's `deliverOne` consumer. Never call it from a handler — and the audit is mechanical: `postToInboxSigned` (the only signed inbox POST) has exactly those two callers, so every activity-building site either calls `enqueueDeliveries` or delegates to a lib that does (routes, inbox handlers, cron, collections, quotes, relays, migration, featured items). The DLQ (`cf-ap-delivery-dlq`) has its own consumer that records failures in KV (`dlq:delivery:*`, 30 days) and acks. **The consumer resolves the signing key at delivery time** (`resolveDeliverySigningKey`, `lib/activitypub/queue.ts`), so an account deletion must park its key in KV (`actor:key:<actorId>`, 24h, written by `deleteLocalAccount`) **before** the actor row goes: the queue drains seconds later, and without the grace entry every queued `Delete{Actor}` died as a permanent "Local actor or key not found" (acked, never delivered — the self-delete and admin-delete paths had the same hole). The row always wins, so a stale entry can never impersonate a live account.
- **Inbound signatures**: `verifySignature` requires `(request-target)` and, when there is a body, `digest` **inside the signed-headers list**; the inbox routes also require a valid `Date` (12h window). Only RSA/hs2019 is accepted.
- **Actor id binding**: never cache an actor document whose `id` differs from the URL that was fetched; `upsertRemoteActor` must never update `is_local = 1` rows (cache-poisoning guard).
- **Domain blocks** (`instance_domain_blocks`): `severity = 'suspend'` drops the activity; `'silence'` processes it but strips media (`reject_media`) and ignores forwarded Flags (`reject_reports`).
- **Inbound reports (Flag)**: `handleFlag` resolves the target account(s) and evidence statuses (unknown ones fetched, cached and host-checked) and stores one `reports` row per target, then runs the same Guardian pipeline as local reports. **Mastodon only forwards a report when the reporter ticks the target's domain in "Forward to"** (`ReportService#forward?` requires the `forward` option; the Flag is signed by the reporting instance's representative account), so a remote report can legitimately never arrive — an empty `reports` table is not a bug. The **outbound** half is the same switch: a local report of a remote account with `forward: true` sends `Flag{object: [target, ...statusUris]}` to that account's inbox (`buildFlag`, delivered through the queue; `reports.forwarded` records it), so the origin's admins get the evidence and can act. Their **decision comes back through the actor document**, not through the report: a suspended account advertises `toot:suspended`, `applyRemoteSuspension` stores it as `suspension_origin = 'remote'` (a suspension **we** applied — `'local'`, the column added by `scripts/057-*` — is never overridden by a fetch, mirroring Mastodon's `ProcessAccountService#set_suspension!`) and the inbox's `Update{Actor}` branch broadcasts `account.updated` so connected clients drop the posts. **The evidence stays visible**: a suspension nulls the posts' content (`suspendAccount`), so the admin report view recovers the text from the stored AP document (re-rendering its Emoji tags), includes the attachments and keeps a placeholder for a post that no longer exists — an admin judging a report must see what was reported (`test/report-evidence.workers.test.ts`). When the target is local, `notifyReportedAccount` (lib/moderation/actions.ts) creates a `moderation` notification **from the Guardian** (never the reporter, to protect their identity) and emails the owner at most once per day (KV `report:notified:<actorId>`); reports about remote accounts are stored without notifying anyone.
- **Instances that block us / unreachable**: the queue consumer records every delivery failure in `delivery_rejections` (permanent 400/401/403/404/410/422, or `status = 0` for network/timeout/5xx with the actual HTTP status in `last_error`); a later successful delivery sets `last_ok_at`. `/api/v1/graph` exposes `status = 403` as `blockedBy` ("Blocks you") and `status = 0` as `unreachable`, both while `last_ok_at IS NULL OR last_at > last_ok_at`. A permanent HTTP status overrides a transient 0. The circuit breaker skips hosts that failed 3 times in a row (1h).
- **Dedup**: `processInboxActivity` records each signed `activity.id` in `activities` (`INSERT OR IGNORE`) and skips replays. Record only after signature/ownership checks.
- **Boosts (Announce)**: the `announces` join table (actor → object) stores each boost; `createAnnounce` persists the caller's `createdAt` (it drives ordering) and bumps `reblogs_count`/`engagement`. **Timelines surface boosts**: `getHomeTimeline` unions own/followed posts with boosts by own/followed accounts (ordered by the announce time, not the original's `published`; a followers-only original only shows when the viewer follows its author; suspended/blocked boosters and blocked domains are filtered) and `getActorStatuses` includes the profile's boosts by default (`exclude_reblogs=true` turns them off — Mastodon's API default), while `getActorBoosts` serves the profile's **Boosts tab** (`only_reblogs=true`, placed between Posts and Replies; the Posts tab sends `exclude_reblogs=true` and the replies tab has none, matching Mastodon's "Posts and replies"). Both return `TimelineEntry[]` (`{ object, boost }`) and routes serialize the wrapper with `serializeReblog` (empty content, booster as `account`, original under `reblog`; wrapper ids are announce ids so cursors resolve via `resolveTimelineSortCursor`). `handleAnnounce` broadcasts the wrapper to the booster's local followers' home streams (`broadcastNewBoost`), and the client renders the "boosted" header in `StatusCard` while interactions/updates merge into the nested `reblog` (`applyStatusInFeed` / `applyStatusUpdateInFeed`).
- **Ownership**: embedded objects in Announce/Update must be authored by the signer or share origin; MLS mutations are actor-scoped (`setMlsKeyPackageActive`, `deleteMlsKeyPackageByObjectId`, `deleteMlsMessagesByObjectId`); call events are validated against the `call:<id>` KV session from the `CallOffer`.
- **Custom emojis**: every ActivityPub document we send carries the **source** text (`:shortcode:`) plus the `tag` Emoji array — the actor (`buildActor`) and the notes (`buildNote`: content, summary and contentMap) — because Mastodon's sanitizer has no `img` (`Sanitize::Config::MASTODON_STRICT`) and its formatter only replaces shortcodes, so a rendered `<img>` is dropped and the emoji vanishes (a real Mastodon sends shortcodes in AP and images only in its REST API). `emojiImgsToShortcodes` does the conversion at build time; the stored content and the REST API keep the rendered image with Mastodon's markup (`class="emojione custom-emoji" rel="emoji"`) and the Emoji tag declares the real `mediaType` (a GIF announced as `image/png` is rejected by stricter peers). Since the **stored** content is the AP source, `serializeStatus` re-renders it with the emoji list and, when a caller does not pass the catalogue (POST responses, favourite/reblog/bookmark routes, conversations, stream broadcasts, scheduled publishes), falls back to the object's AP `tag` emojis (`emojisFromRaw`) — without that fallback a just-published reply or an interaction response kept the `:shortcode:` as plain text until a reload. Account **notes** are rendered the same way by `serializeAccount` from `opts.emojis`: every route returning accounts whose bio the client shows (profile, **followers/following lists**, suggestions, verify_credentials) must pass `getAllCustomEmojis(env.DB)` — the followers/following routes forgot it and the lists kept the shortcodes.
- **Mentions carry the actor IRI**: the linkifier (`processStatusContent`) has no DB access, so for remote mentions it can only build the web profile (`https://domain/@user`). Every note-building path canonicalizes the Mention tags (`canonicalizeMentionTags`, lib/activitypub/mentions.ts) before building the Note: cached actors resolve offline, unknown ones through `fetchAndCacheRemoteActor` (profile URL → same-host canonical id, id-binding check included). A `/@user` href makes peers skip the mention notification — and the delivery, when the peer does not serve the actor at that URL (Mastodon serves HTML there). The inbox is lenient the other way: a Mention href on our host that is not the exact actor id (`/@user`) is mapped to the local account (`resolveLocalMentionedActor`), so activities from peers that still send the old shape notify too. The local notification loop uses the canonical tags, which also covers a full-handle local mention (`@user@ourdomain` arrives as the remote `/@user` shape).
- **Only mentions that resolve to an account are rendered as links**: the renderers take a `MentionsMap` (`lib/activitypub/content.ts`) and an `@word` that is not in it stays plain text. The create/edit routes build it with `resolveMentionLinks` (`lib/activitypub/mentions.ts`: one batched local lookup via `json_each`, cached-then-fetched remote resolution, plus the reply's conversation participants) **before** rendering, so `@algo` typed by mistake gets neither a dead `/users/algo` link nor a Mention tag; admin composers (announcements, instance settings) resolve the same way. `serializeStatus` derives the map from the object's stored AP `tag` array (`mentionLinksFromRaw`) instead of hitting the DB: a bare `@word` in remote HTML is never linked to our own local profile, and a remote mention links to its canonical IRI. The account note/fields (`serializeAccount`, synchronous and DB-less) still linkify every handle.
- **Polls**: a vote arrives as `Update{Question}` with the same body — refresh the counts (`refreshPollFromQuestion`) **without** `updateObject`, which would stamp `updated_at` (the status reads as "edited") and record an empty edit-history row; a real content change still takes the normal path. `ensurePollRowsForQuestion` creates the rows **and applies the document's per-choice counts**, and also runs when an object is reused (`persistRemoteNote` existing branch) or announced again (`handleAnnounce`), so a Question cached without poll rows gets them (and its results) on the next announce. Every serialization that can show a poll must load it: boosts (`broadcastNewBoost`, and the reblog route response — the client merges it into the timeline and would drop the poll otherwise) and quotes (`serializeQuote`/`getQuotesByIds`, viewer-aware; `QuoteInline` renders it read-only inside the link).
- **Poll statuses are always served as Questions** (`applyPollToNote`, `lib/activitypub/polls.ts`): the object endpoint, the outbox, the edit `Update` and the create `Create` all attach `type: Question` + `oneOf`/`anyOf` (choices with `replies.totalItems` counts), `endTime`, `closed` (when expired) and `votersCount`. Mastodon re-fetches the object URL to refresh a poll's counts (`refreshRemotePoll` does the same for remote polls), so a plain Note there hid the poll from peers; a new AP path that serves local statuses must apply it too.
- **Polls (card + expiry)**: a status card renders a poll **only** as `PollView` — the AP type block's `Question` fallback (which carries "open original") is for bare questions without stored options and used to duplicate every poll with that link *above* the options. The link now sits **below the votes and only for remote polls** (a local poll's origin is this same instance; `/polls/:id` applies the same check through its `?status=` id). When a poll expires the cron notifies the **local voters** plus the author (`notifyExpiredPolls`, Mastodon's `PollExpirationNotifyWorker`): remote polls were the silent case, because their author is remote and the old lazy notification (in the poll GET) only knew the author. The author's notification is the pass's marker (`listPollsToNotify` skips polls that already have it) and `createNotification` returns `false` for a duplicate (the dedup index ignored the insert), so a re-run never delivers the same notification twice; polls expired more than 7 days ago are left alone so a deploy never spams history.
- **Events (composer)**: the compose box publishes an ActivityStreams `Event` (the calendar button between location and schedule; the `event` body field carries `name`, `start_time`, `end_time` and `location`, parsed by `parseEventInput` in `lib/event.ts`). `buildNote` switches the document type and adds `name`/`startTime`/`endTime`; the status text stays the description, so an event may have no text at all. The venue and the status' geolocation are the **same** `location` property, so both are merged into one `Place` (the venue as its name, the coordinates + map URL when the user shared a point). The stored `type` column says `Event` (`resolveAPType` also falls back to the raw type), the cron's `publishDueScheduled` carries the event through, and the edit route rebuilds the document from the new text — `eventFromRaw` feeds the title/time range back in, or an edited event would silently become a plain Note. A **local** event shows no "open original" link (`APTypeBlock`'s `isLocal`, passed by `StatusCard` from the author's `acct`): its "original" is this same instance, the same rule as the poll card.
- **Quote authorizations (FEP-044f)**: `interactionPolicy.canQuote` alone does **not** make a quote visible on Mastodon 4.4+ — `ActivityPub::VerifyQuoteService` only accepts a quote whose note carries a `quoteAuthorization` issued by the **quoted** post's server, so a quote without it renders as "pending approval" indefinitely. `lib/activitypub/quotes.ts` owns both halves: a local status quoting a **local** post mints the authorization on the spot (`ensureLocalQuoteAuthorization`, served at `/quote_authorizations/<id>` as a real `QuoteAuthorization` document — never a fragment IRI, which resolves to the actor document and gets the quote rejected); quoting a **remote** post sends a `QuoteRequest` (`object` = the quoted post, `instrument` = our status) and the `Accept` that comes back carries the approval URI in `result`, which `handleQuoteAccept` validates (https + the quoted account's host + our status is the one quoting it) and stores with `setObjectQuoteAuthorizationUri` — **not** `updateObject`, which would stamp `updated_at` and mark the status as edited — before redistributing the note as an `Update` so the instances that already stored the post accept the quote. Inbound, a remote `QuoteRequest` is answered with an `Accept` (public/unlisted, no block between the accounts) or a `Reject` (private/direct: there is no manual approval UI) by `handleQuoteRequest`, which records the `quote_authorizations` row the Accept points at.
- **Outbound activity shapes follow Mastodon's serializers** (`lib/activitypub/utils.ts`): `Undo` mirrors the wrapped activity's `to`/`cc` and never invents an audience — `Follow`, `Accept`, `Reject`, `Move` and `Like` carry **no** audience at all (Mastodon's serializers omit it; the recipient is the delivery target, not an audience), and the relay `Follow`/`Undo` pair matches `Relay#unfollow_activity`. `Move.object` is the **origin** account (`MoveSerializer`, and Mastodon's handler rejects the activity unless `origin_account.uri == object_uri`) with the destination in `target`; `Delete{Note}` wraps a Tombstone, while `Delete{Actor}` (`buildActorDelete`) sends the **bare actor URI** as `object` with the deterministic id `<actor-uri>#delete` (Mastodon's `DeleteActorSerializer`; peers match `object` against the signer's URI to purge the account). Notes always declare `interactionPolicy.canQuote.automaticApproval` (public/unlisted → `Public`, private → followers, direct → the author): a missing policy resolves to `:denied` on Mastodon 4.4+, so nobody could quote our posts. They also advertise the `likes`/`shares` collections with their counts and, for threads, the OStatus `conversation` (`conversationUri` — a root starts `tag:<domain>,<date>:objectId=<id>:objectType=Conversation`, a reply joins its parent's stored one via `conversationFromRaw`; notes append `OSTATUS_CONVERSATION_CONTEXT` so the short key resolves to `ostatus:conversation` rather than the MLS term `DEFAULT_CONTEXT` carries). Actors advertise `webfinger` and Mastodon's profile settings (see below). Deliberately absent: `memorial`/`suspended`/`attributionDomains`-style fields are only sent when set, and `attributionDomains` only when non-empty (Mastodon's conditionals). Every property we serialize must be declared in the context (`lib/activitypub/vocab.ts`) — `sensitive`, `blurhash`, `votersCount`, the `gts:` interaction-policy terms, `showFeatured`/`showMedia`/`showRepliesInMedia`, `attributionDomains` (`@container: @set`), FEP-044f `quote`, FEP-7aa9 `featuredCollections` — or a JSON-LD processor drops it.
- **Featured items federate; the profile recommendation does not**: pinning a status (`POST /api/v1/statuses/:id/pin`) or featuring a hashtag (`POST /api/v1/featured_tags`) sends Mastodon's `Add`/`Remove` (`ActivityPub::AddSerializer`/`RemoveSerializer`: `type`/`actor`/`object`/`target`, **no `id`** and no audience — the followers are the delivery target, not a `to`/`cc` list) through the queue (`deliverFeaturedChange`, `lib/activitypub/featured.ts`, `buildFeaturedActivity`). `object` is the status IRI for a pin and a `Hashtag` document (`{ type, href, name }`, Mastodon's `HashtagSerializer`) for a tag; `target` is the collection the actor advertises — `/users/:username/collections/featured` (an `OrderedCollection` of status IRIs) and `.../collections/tags` (a `Collection` of Hashtag objects), served by `app/users/[username]/collections/{featured,tags}/route.ts` with Mastodon's 3-minute cache: both were advertised in the actor document but **404'd**, so a peer (or `fetchAndCacheRemoteActorFeatured` on our side) could never resolve them. Recommending an **account** (`POST /api/v1/accounts/:id/pin`, Mastodon's `AccountPin`) stays local — Mastodon's model has no AP callbacks, so there is nothing to federate — but it validates that the account **follows** the target (Mastodon's `pin_errors.following`, 422), and the profile pages take `endorsed` (and `note`) from the relationship: both were missing from the client state, so the star and the private note looked lost on every reload (the local page also had its endorse labels hardcoded in Spanish).
- **Actor profile settings (Mastodon's ActorSerializer)**: `actors.memorial`/`show_featured`/`show_media`/`show_media_replies`/`attribution_domains` (added by `scripts/053-*` + `upgrade-schema.mjs`; run it **before** deploying — the suggestion pools filter on `memorial`). Outbound: `buildActor` always sends the three display toggles (defaults true), `memorial: true`/`suspended: true` only when set and `attributionDomains` only when non-empty; a **suspended** local actor still serves its actor document with `suspended: true`, and suspending/unsuspending **distributes it** (`broadcastActorState` sends the `Update{Actor}` to the accepted followers — Mastodon's `SuspendAccountService#distribute_update_actor`; the document alone is only read on a refetch, and a suspended account never posts again to trigger one — and `broadcastActorUpdate` must keep sending `suspended`/`memorial` or a broadcast tells peers a suspended account is active again). A suspended account is also **disconnected locally**: the web profile shows the notice (`account_suspended_title`/`_desc`) instead of the tabs, hides the follow button (an existing follow keeps its unfollow, like Mastodon, so the relationship can be severed), the message/call actions and the anonymous follow link — **on both profile pages**: `app/users/[username]/page.tsx` (local accounts) and `app/users/remote/page.tsx` (the page a remote account is opened in, which used to render it as if nothing had happened), `/api/v1/accounts/:id/statuses` returns nothing (its content is "removed publicly"), **its notifications are not served either** — `getNotifications` and `getUnreadNotificationCount` filter suspended senders with a `NOT EXISTS` primary-key probe per candidate row (so the list and the badge agree; the rows survive and a reinstatement brings them back), a notification that arrives **while** the account is suspended is stored but not delivered (`createNotification` returns false for a suspended sender: no stream event, push or email, so a stale activity from its server cannot interrupt anyone) and `broadcastAccountUpdate` pushes `account.updated` to the `notification:<username>` channels of the accounts that received a notification from it (they are not necessarily followers, so the home fan-out does not reach them) so an open notifications list empties on the spot — and **nothing the account wrote keeps being served** (Mastodon's `SuspendAccountService#purge_profile!`): `serializeAccount` returns the instance defaults (`default-avatar.png`/`default-header.png`) for the avatar and header, the username as `display_name`, an empty `note` and no `fields`, while `buildActor` omits `icon`/`image`/`attachment` and sends the username as `name` with an empty `summary` — so moderation does not keep distributing what the account uploaded or wrote. Only the handle survives (that is what identifies it); the stored values stay in D1/R2 and a reinstatement brings them back (asserted end-to-end in `test/suspend-account.workers.test.ts`). The **status permalink** of a suspended author is a 404 as well (`GET /api/v1/statuses/:id` checks `author.suspended`, mirroring Mastodon's `StatusPolicy#show?` refusing `author.unavailable?`), so the attachments and the card are not reachable either; only the owner still reads its own statuses. Inbound: `upsertRemoteActor` stores them — `memorial` and the domains **clear** when the document omits them (Mastodon's `@json['memorial'] || false` / `attributionDomains || []`), while the display toggles only update when the key is present (the stored value is read first: binding NULL into their NOT NULL columns aborted the whole upsert into the silent legacy fallback). It also applies the document's `suspended` through `applyRemoteSuspension` (`actors.suspension_origin`, `scripts/057-*`): a remote suspension is stored and cleared when the origin lifts it, a local one is never touched. `normalizeAttributionDomains` mirrors Mastodon's normalization (no scheme/`*.`, unique, ≤100). REST: `serializeAccount` always exposes `show_media`/`show_media_replies`/`show_featured`, `memorial` only when set and `source.attribution_domains` for the current user; `PATCH /api/v1/accounts/update_credentials` accepts `show_*` and `attribution_domains` (Mastodon's own endpoint accepts the domains; its `PATCH /api/v1/profile` — with avatar/header descriptions — is not implemented). UI: the profile page shows the "In memoriam" banner and hides the featured/media tabs per the account's settings (the media grid includes replies unless `show_media_replies` is off), `/settings` edits the toggles and `/settings/verification` the attribution domains. Moderation: `POST /api/v1/admin/accounts/:id/memorialize` (full admin, `accountActionGuard` with `removesAccess`) preserves the account in memoriam, emails the owner and logs it; memorialized accounts cannot sign in (`getAuthenticatedActor`, the password grant's `login_error_memorial`, `/api/auth/status`'s `memorial` reason) and are excluded from the suggestion pools (`without_memorial`).
- **Limited (silenced) accounts** (`actors.silenced`, admin → Limit): Mastodon's "Limit" behavior. Hidden from every public surface (local/federated/hashtag timelines, trends, public-stream broadcasts, directory, suggestions, follow recommendations, oEmbed) while its content stays visible to followers (home timelines) and on its profile, and the REST account carries `limited: true`. It does **not** affect federation (nothing is delivered to peers) and is reversible. Two rules go beyond visibility: a follow **from** a limited account becomes a follow request even when the target does not require approval (`FollowService#call` → `request_follow!` for `@source_account.silenced?`; inbound `ActivityPub::Activity::Follow` → `target_account.locked? || @account.silenced?`), and notifications from a limited account are **filtered** by default (Mastodon's `NotificationPolicy#for_limited_accounts` = filter): stored with `notifications.filtered = 1` (`createNotification` returns whether to deliver, so no stream/push/email), hidden from `/api/v1/notifications` unless `include_filtered=true` (the web UI's "Filtered" tab), excluded from the unread count and serialized with `filtered: true` — unless the recipient follows the sender. Limited accounts stay **findable in account search** (Mastodon's `Account.searchable` excludes suspended/moved only), so they can still be mentioned and followed; status text search stays closed (a discovery surface).
- **Status collections**: the note's `likes`/`shares`/`replies` URLs are served by `app/objects/[id]/[collection]/route.ts` (Mastodon's `ActivityPub::LikesController`/`SharesController`/`RepliesController`): likes/shares are count-only `Collection`s, replies a `Collection` whose `first` page lists the reply IRIs oldest-first (public/unlisted, `media_pending = 0`), cursor-paginated with `min_id`. Only public/unlisted local objects expose them. The outbox collection carries Mastodon's `last` link (`?page=true&min_id=0`), which **resolves to the oldest page** (Mastodon's own pagination returns the newest page for it — ours does what the link says).
- **Profile feeds (RSS/Atom)**: `lib/feeds.ts` mirrors Mastodon's `AccountsController#show` RSS branch (`app/views/accounts/show.rss.ruby`): **public + unlisted** posts, **no replies and no boosts**, newest first, `?limit=` (max 200) and `?max_id=`. Per item: the CW preroll (`<strong>CW</strong><hr>`), the rendered content (custom emoji sized inline like Mastodon's `SYNDICATED_EMOJI_STYLES` — readers have no site stylesheet), the poll options as disabled inputs, the hashtags as categories and the attachments as Media RSS `media:content` plus an `enclosure` for the first audio (Mastodon's podcast support). Served at `/users/:username/rss` and `/users/:username/atom` (`application/rss+xml` / `application/atom+xml`, `Cache-Control: public, max-age=60`), with Mastodon's `/@username.rss` and `/@username.atom` rewritten by `proxy.ts`; the profile page advertises both with `<link rel="alternate">` (React 19 hoists them into the head). **Local accounts only** (Mastodon's route constraint excludes remote handles) and a **suspended** account has none (its content is not served), while a limited (silenced) one keeps serving it like its profile. **Every profile advertises them when the server hosting the account serves them**: the profile endpoints (`lookup` and `/api/v1/accounts/:id`) fill the account's `feeds` through `discoverProfileFeeds` (`lib/feed-discovery.ts`) — ours for a local account, in Mastodon's public shape (`https://domain/@user.rss|atom`, which `proxy.ts` rewrites to the feed routes) and from `getBaseUrl(env)`, never the request Host, and for a remote one a one-off probe of `/@user.rss` and `/@user.atom` cached in KV (a hit for a week, a miss for a few hours, so a link to a 404 is never shown) — and both profile pages render the RSS/Atom buttons after the follow button. A suspended account gets none either way: linking out to the origin would contradict the suspension. The description is localized with the instance's primary language (`languages` setting → `rss_feed_description`).
- **Markdown for agents (content negotiation)**: a client that prefers `text/markdown` in its `Accept` header gets the document **built from our data**, not the HTML shell: the status permalink and the profile pages are client-rendered React views whose server HTML carries no content (the data is fetched from the API in the browser), so converting the shell — what an edge HTML→Markdown converter does — would return nothing. `proxy.ts` rewrites `/statuses/:id`, `/users/:username` and `/@username` to `app/md/{statuses,users}/…` when `acceptsMarkdown` (`lib/markdown-agents.ts`, q-values included, so a browser sending `text/html` or the wildcard never gets markdown — `lib/markdown.ts` is the **authoring** side, md→HTML for the composer) says so; the routes answer `text/markdown; charset=utf-8` with `Vary: Accept` and the same visibility rules as the pages (a suspended author is a 404, a followers-only status is served to its audience with `private` caching). `htmlToMarkdown` converts the content HTML this app renders (the tag set `lib/activitypub/sanitize.ts` allows; custom emoji become their `:shortcode:`, Mastodon's shortened links collapse to the bare URL, block-looking lines are escaped, script/style content is dropped) and the `*MarkdownDocument` builders compose the documents (CW, media, poll, link card, metrics, permalink and AP IRI; profile fields and recent public posts). Deterministic and synchronous — no AI conversion, no per-request cost.
- **`Delete` cleanup** lives in `deleteObject` (notifications, conversation pointer, parent `replies_count`/`engagement`) and `deleteRemoteActorData` (`Delete{Actor}` purge). `Undo{Accept}` removes followers; `Undo{Follow}` only decrements accepted follows. A `Delete` whose signer key cannot be fetched right now (`no-key`) is acked as a delivered no-op (202) when neither the signer nor the target object is cached — retrying those forever flooded the inbox with 5xx when a sender was unreachable from Cloudflare's egress (masto.es, HTTP 525 on every fetch); anything cached still answers 503 so an unverifiable Delete can never remove stored data.
- **Profile moves (Move)**: `lib/activitypub/migration.ts` is the outbound half (`/settings/migration` → `POST /api/v1/accounts/migrate`): WebFinger resolves the destination, the destination must list the source in `alsoKnownAs` (refreshed once before refusing — the "you may need to wait up to 24 hours" of the Mastodon docs), then the source records `movedTo`, **every local follower is re-pointed and sent its own `Follow` signed by that follower** (the target's instance only learns about a follower from a Follow: without it the account arrives at the new instance with no followers), the source's `followers_count` drops by the accepted ones, and the `Move` goes to the remote followers **and to the destination instance** through the queue (`collectFollowerInboxes`, shared inboxes preferred; `delivered` counts **servers**, i.e. distinct inbox domains, which is what the UI reports). Telling the destination is deliberate: setting up the alias made it fetch and cache the old account, and Mastodon only reads `movedTo` on a re-resolve (`ProcessAccountService`, refetched when the cached copy is over a day old), so without the Move it keeps showing a followable profile with no "moved" notice; the cached actor document (`ap:actor:<username>`, 5-minute KV entry) is dropped at the same time. `handleMove` (inbox) is the inbound half: alias verified, source marked `movedTo`, local followers re-pointed and re-followed. **Aliases are the destination half of a move**: Mastodon only offers them in its web UI (Preferences → Account → "Moving from a different account") with no REST endpoint, so `/settings/migration` plus `GET/POST/DELETE /api/v1/accounts/aliases` (`lib/activitypub/aliases.ts`) let a local account declare them — the handle is resolved against the local DB (never a self-fetch: a Worker fetching its own hostname times out with HTTP 522) or WebFinger + the hardened actor fetch, the IRI is stored in `actors.also_known_as`, served by `buildActor` and pushed to the followers with `broadcastActorUpdate` (`lib/activitypub/actor-update.ts`, shared with the profile save) so the old instance verifies the Move immediately instead of on its next fetch. **A moved profile shows a banner, it does not HTTP-redirect** (Mastodon's `AccountBanners`/`MovedNote`): the REST account carries `moved` (`serializeAccount`'s `opts.moved`, `authorMoved` for statuses) — **every** route the client renders as a profile must fill it: the web profile reads the account from `/api/v1/accounts/lookup`, which used to omit it, so a migrated account kept its follow button and showed no notice (`getMovedAccount`, `lib/mastodon/account-extras.ts`, shared with `/api/v1/accounts/:id` and `verify_credentials`), the actor document carries `movedTo` (which is what peers render), the web profile shows the notice with a link and **hides the follow button** unless already following. A moved account is also **hidden from discovery** — suggestions (`getAccountSuggestions`), account search and the directory filter `moved_to IS NULL`, like Mastodon's `Account.searchable` scope (`where(moved_to_account_id: nil)`) — and `/settings/migration` states what actually moves: only followers (and the notice); posts and the accounts you follow are not transferred (Mastodon's `migrations.other_data`, with a link to Import/Export).
- **Follows**: the follow route stores a remote follow optimistically as `accepted` (`pending` only for `manuallyApprovesFollowers`) and increments `following_count`; `Reject{Follow}` flips the row to `rejected`, undoes that increment (a pending request never counted) and broadcasts a `relationship` event with the generic `broadcastEvent` on the local follower's `user` stream so open profile pages refetch the button (`Accept{Follow}` does the same for a pending row). A rejected row is not permanent: a new inbound `Follow` re-opens it, and `POST /follow` re-sends the activity with a fresh id. `POST /api/v1/accounts/:id/remove_from_followers` deletes the follow and, when the removed follower is **remote**, tells it with a `Reject{Follow}` (wrapping the original Follow, `follows.activity_id`) to its **personal** inbox through the queue — Mastodon's `RemoveFromFollowersService`, which notifies nobody when the follower is local. `deleteRemoteActorData` subtracts the cascading follows from the local counters before the purge.
- **Remote accounts require auth**: `/api/v1/accounts/:id` (401 for anonymous remote ids, cached or not), remote `lookup` handles, `/api/v1/accounts/:id/statuses`, `/api/v1/accounts/:id/collections`, the `/users/remote` page, `/api/v2/search` remote resolution, `/api/v1/statuses/:id` on-demand resolution and `/api/v1/e2ee/resolve`. Local profiles stay public. Discoverable collection pages (`/api/v1/collections/:id` and `/collections/:id`) stay public even for remote collections. `/api/v1/accounts/search` accepts a plain username (prefix), a display-name substring, a handle with or without the leading `@` (Mastodon's `AccountSearchService` strips one — the composer autocomplete sends what the user typed, so `@user@domain` used to return nothing) and a pasted profile URL (`https://domain/@user`, `https://domain/users/user`), resolving the account before the text search (`parseAccountQuery`, `lib/account-search.ts`); cached remote results stay authenticated-only and `resolve=true` fetches an uncached one via WebFinger.
- **Remote handle URLs are link-outs, never resolution**: `/@user@domain` is rewritten by `proxy.ts` to `/redirect?url=…` (Mastodon's "you are about to leave" interstitial pointing at `https://domain/@user`); direct `/users/user@domain` visits redirect there too. Same-instance handles (`/@alice@cf-ap.com`) stay local.
- **Outbox**: `buildOrderedCollectionPage(collectionId, pageId, items, nextId?, prevId?)`; `totalItems` counts only public statuses; cursor advances with the last fetched status regardless of visibility; suspended actors 404. Collections are CORS-enabled via `proxy.ts`.
- **Collections** (FEP-7aa9): local actors advertise `featuredCollections` and serve `/users/:username/collections` (+ `/collections/:id`, `/feature_authorizations/:itemId` for local item accounts). Mutations enqueue `Update`/`Delete{FeaturedCollection}` to followers. Remote collections are cached by `syncRemoteCollections` (KV throttle 1h; forced by inbound `Update{FeaturedCollection}`, removed by `Delete`) via the account/collections routes; `collections.url` stores the remote web URL and `collectionHref()` picks the right link. Caption/description edits on remote collections are only mirrored on sync.
- **Scheduled statuses** publish through `createObject` + `enqueueDeliveries` + streaming (public/home) and link pending media (`pending_media:` KV, TTL extended at schedule time). Don't hand-roll inserts there.
- **Consume or cancel every outbound response body** (`discardBody` in `lib/http.ts`): leaving bodies unread stalls the runtime's in-flight fetch pool and triggers "A stalled HTTP response was canceled to prevent deadlock" (deliveries/push only need the status; R2 rejects streamed uploads without a known length — use `FixedLengthStream`, and cancel the stream if `R2.put` fails).
- **SSRF**: run `safeFetch` (or at least `validateOutboundUrl`) before every outbound request. `safeFetch` re-validates each redirect hop and bounds the whole exchange with a timeout; it blocks private/metadata/CGNAT/multicast ranges and internal suffixes (DNS rebinding is out of scope inside a Worker) and returns `null` — never throws — when the fetch itself fails (DNS, TLS, the timeout abort), because every caller only handles "a response or null" and an unreachable origin must not turn a route into a 500.
- **Every outbound federation request carries a User-Agent** (`federationUserAgent`, set by `safeFetchTracked` when the caller sends none; the media cache's own UA via `fetchWithUserAgents` is respected): Cloudflare Workers' `fetch` sends none by default and strict servers reject such requests outright — GoToSocial answers **418 "I'm a teapot: no user-agent sent with request"** to WebFinger, actor documents and inbox deliveries alike. The search route's bare WebFinger fetch was silently 418'd, so `@user@gts.example` never resolved in Explore even though the signed actor fetch (which does set a UA) worked; `fetchRemoteObject` and `postToInboxSigned` had the same hole.

### Federation engine (instances)

- **Registry + metadata**: `instances` (one row per remote domain) stores NodeInfo metadata and availability. `lib/activitypub/instances.ts` fetches `/.well-known/nodeinfo` (2.1 → 2.0 → 1.0, SSRF-guarded) with a `/api/v2/instance` fallback; the cron refreshes due instances (`INSTANCE_REFRESH_BATCH`/`_DAYS`) and, daily, expires the metadata of dormant instances (`INSTANCE_DORMANT_DAYS`, kept if a local account follows them). `/api/v1/instance/peers` reads the registry.
- **Availability (Mastodon `DeliveryFailureTracker`)**: failures on 7 distinct UTC days mark a host `unavailable` and set KV `inst:down:<domain>` (24h) so the queue consumer skips it without a D1 read; any success clears it — outbound delivery or a **signed inbound activity** (`recordInstanceInboundActivity`, KV-throttled last_seen). This is the only recovery path for hosts we stopped delivering to.
- **Delivery target**: `collectFollowerInboxes` prefers `endpoints.sharedInbox` (stored in `actors.shared_inbox`). New/updated actors populate it from their AP document; the cron backfills the actors that matter (`backfillRemoteSharedInboxes`, `SHARED_INBOX_BATCH` per tick, failures parked in KV `actor:shared:skip:*` for 7 days). Per-user inboxes are noisier and time out on some implementations (GoToSocial…).
- **Retries (Mastodon `ActivityPub::DeliveryWorker`)**: `max_retries = 16` in `wrangler.toml`, delay `(attempts^4)+15+jitter` capped at 24h (`deliveryRetryDelay`), `Retry-After` honored for 429/503; permanent 4xx ack; exhausted messages go to the DLQ.
- **Admin**: `/admin/instances` + `/api/v1/admin/instances` (list/filter, add/refresh, reset availability, suspend/unsuspend, purge all cached actors of a domain). Suspend sets the KV `inst:paused:<domain>` marker that the queue consumer checks (delivery stops); purge uses `deleteRemoteActorData`; actions are written to `moderation_log` with `target_type = 'instance'`.

### Relays (ActivityPub relay subscriptions)

- An admin adds a relay by its **inbox URL** (`/admin/relays`, `/api/v1/admin/relays`; `relays` table with `idle|pending|accepted|rejected`). Enabling sends `Follow{object: as:Public}` — Mastodon's `Relay#follow_activity`, not the relay's actor URL — signed by the reserved instance actor (`getInstanceSigner`) and parks the row in `pending`.
- `Accept{Follow}`/`Reject{Follow}` are matched by `follow_activity_id` and only from the relay's own host/inbox (`relayMatchesActor`: recorded `actor_uri`, then inbox/shared inbox, then same host — the first answer has no actor URI yet) → `accepted` (+`actor_uri`) or `rejected`. `/admin/relays` polls while a subscription is `pending` (5 s, skipped in background tabs, refetch on focus) so the table flips to `accepted` on its own — no websocket involved. A rejected relay stays re-enableable. Disabling sends `Undo{Follow}` and returns to `idle`; removing an enabled relay unsubscribes first; every mutation is audited (`moderation_log`, `target_type = 'relay'`) and needs a full administrator (moderators only read).
- An `Announce` from an accepted relay is stored as a **normal remote status, never a boost** (`storeRelayedStatus`): the announced object is taken embedded or fetched, attributed to its real author, and the author's own instance domain block applies (the relay signed, not the author — suspend drops it, silence strips media). An announce from a **known but not accepted** relay is ignored outright (never boosted). A status whose remote media is still caching stays held (the media release announces it later), an already stored object is skipped, and live fan-out goes through `broadcastStatusCreatedToAudience`.
- **Relays that forward the original activities** (`activity-relay` — relay.toot.io, relay.intahnet.co.uk — and Mastodon's relay mode) send the third-party `Create`/`Update`/`Delete` **signed by the relay itself**, so the HTTP-signature signer legitimately differs from the activity's `actor`. `processInboxActivity`'s anti-spoofing check allows that cross-actor case **only** for those content types, **only** while the subscription is `accepted` and **never** when the author is local (`isAcceptedRelayForward`), and judges the activity by the **author's** instance block (like `storeRelayedStatus`). Those relays publish their instance actor with the older **PKCS#1** key (`-----BEGIN RSA PUBLIC KEY-----`): `security.ts` wraps it in the SPKI envelope before importing (`publicKeyDer`/`pkcs1ToSpki`) — without that every delivery from them failed verification with "invalid" in the inbox logs (their Accept never processed, so they stayed `pending` forever).
- **Outbound**: every local **public** status is also delivered to each accepted relay's inbox (`withRelayInboxes` / `acceptedRelayInboxes`, Mastodon's `StatusReachFinder#relay_inboxes`) so the relay re-broadcasts it to its other subscribers — creates, edits and deletes, including scheduled publishes and the auto-delete cron. Unlisted/private/direct statuses never go to relays.

### Account expiration (inactivity)

- `lib/moderation/account-expiration.ts` runs from the cron (`setStage("expiration")`, 5-minute KV throttle). With the feature **enabled by default** (`account_expiration_enabled` / `account_expiration_months` = 12, editable in `/admin/settings` → `PUT /api/v1/admin/instance_settings`, months clamped to 1..120), a local account inactive for the whole window is warned by email **7 days** and again **24 hours** before expiring, **suspended automatically** when the window passes (`suspended = 1` + `suspended_at`, logged as `suspended`, `model: "expiration"`) and **deleted one month after the suspension** — whatever the suspension origin — without further warnings.
- `last_active_at` is the clock: `getAuthenticatedActor` refreshes it (throttled to one write per hour, so any authenticated request counts as activity) and drops the KV warning markers (`expiry:warn:7|1:<actorId>`), so a returning user starts a fresh window; `createActor` seeds it at registration and `upgrade-schema.mjs` backfills accounts that never signed in from `created_at` (and `suspended_at` from `updated_at`, then from the latest `moderation_log` suspension for anything still missing — cached remote accounts suspended by a domain block). Warning/suspension candidates walk `idx_actors_expiry`, the purge walks `idx_actors_suspended_at` (ordered scans, early stop; one branch per `is_local` value — a single query without that equality loses the index). Administrators, moderators, the reserved instance actor and accounts **in memoriam** are **exempt**: a background sweep must never remove a privileged or preserved account. `suspended_at` is stamped by every suspension path (`suspendAccount`, the admin route, the registration sweep, the expiration sweep and domain blocks) with `COALESCE(suspended_at, ?)`, so re-suspending never resets the purge clock, and unsuspending clears it; the admin accounts table shows both the suspension date and the scheduled purge date (`purgeDateFrom`, `lib/purge-date.ts`) — and suspended accounts are **not** listed in `/admin/accounts` (any status filter but `suspended` excludes them): they have their own table, `/admin/suspended`, which shows the suspension and the scheduled deletion dates.
- The purge covers **local accounts** (federated `Delete{Actor}` to the accepted followers — parking the actor's signing key in KV first, because the queue consumer signs at delivery time, see the delivery bullet above — uploads removed from R2, `oauth_tokens`/`activities`/`moderation_log` dropped, actor row and cascades gone) and **cached remote accounts** (the canonical `deleteRemoteActorData`: counters, notifications and the row; nothing is federated, we are the ones who suspended them — the media cache maintenance then drops the orphaned entries). Both record a moderation entry.

### Licenses (FEP-6757 content licensing)

- The catalogue lives in `licenses` (admin screen `/admin/licenses`, `/api/v1/admin/licenses`; public list `/api/v1/licenses`). Canonical license URIs only — the FEP forbids deeds, localized URLs and SPDX ids. The seed (marker `seed:licenses`, replayed by the upgrade script) is the six Creative Commons licenses plus CC0, the public domain mark and “In copyright”; a removed entry is never re-created. The admin edits the **icon URL** (`licenses.icon`, optional) and the **Fork Awesome badge keys** (`licenses.badge_keys`, space-separated like `cc cc-by` or `copyright`, with a live preview, a Badge column and a link to the Fork Awesome gallery; editing prefills the keys with the stored ones or the ones derived from the URI), and clients resolve a license as **icon image (`licenses.icon`, the seed ships the official CC buttons) → stored badge keys → badges of a known URI → the letters of its id** (`licenseVisual`), so a custom license from a peer still renders (`MI-LICENCIA`) and an operator can give any entry a readable badge without hosting an image. Every default catalogue entry ships with its keys (`cc cc-by`, `cc cc-zero`, `copyright`…; the `seed:license_badges` marker backfills instances seeded before the column existed, guarded by `badge_keys = ''` so an admin edit is never overwritten, and the script renames the short-lived `badge_text` column).
- License icons go through the **media cache** like any other remote resource: the admin route and the lookup enqueue them (`enqueueMediaCache(..., "license", id)`), the cron drains the catalogue ones (`listLicensesMissingIconCache`), and the API/lookup serve the R2 copy (`cachedMediaUrl`) while the row keeps the origin URL — so expiry/purge needs no reset. `listOrphanMediaCache` keeps a `license` entry alive while some `licenses.icon` points at it.
- `/api/v1/licenses/lookup?url=…` resolves a license that is not in our catalogue by asking the **origin instance** (`<origin>/api/v1/licenses`, KV-cached 7 days, SSRF-guarded): a peer's custom license arrives with its real name and icon, and the client otherwise falls back to the letters of its id plus a link to the origin's page.
- A status stores `objects.license_url` (deliberately **not** a FK), so removing a catalogue entry never strips a published post of its licensing. `buildNote` sends it as the Dublin Core `license` property with the `https://w3id.org/fep/6757` context; the actor sends `preferredLicense` from the `posting:default:license` preference. Absent means “all rights reserved”.
- Composers offer a `LicensePicker` next to the visibility picker (default from settings, “no license” = none); the status card shows the license badges linking to `/licenses/<id>` (catalogue) or `/licenses?url=…`. Badges derive from the URI (`licenseIconsForUrl`), so licenses from remote instances render too, and the picker/settings remind the user that federation means nobody can enforce the license afterwards.
- Inbound: `extractLicenseUrl` reads `license` / `schema:license` / `cc:license` into `objects.license_url` on every remote-store path (handleCreate, persistRemoteNote, remote.ts).

### Remote media cache (R2)

- Federated resources (status attachments, profile avatars/headers) are cached in R2 (`media_cache` table, `cache/media/<sha256>.<ext>` keys) and served from `/api/media/...`, so clients stop hitting the origin server. `attachments.remote_url` / `actors.avatar_url` keep the origin; the served `url` / `avatar_cache_url` point at the cached copy (serializers prefer the cache URL). Entries are keyed by source URL and `cached_url` is applied to EVERY attachment/actor referencing that URL (the same file backs several posts), and enqueueing an already-cached URL rewrites new references on the spot without waiting for the cron.
- **Remote media while it is being cached (no blank posts)**: a freshly ingested remote status is flagged `objects.media_pending = 1` while its attachments **and the author's avatar** are still being cached, and it is served and streamed right away **with the origin URLs** — holding it out of the feeds (and stripping media/card in `serializeStatus`) left the post blank in timelines, notifications and permalinks for as long as the queue was behind. Once the media is in R2 (or permanently failed) the cron releases it (`releaseMediaPendingObjects`) and broadcasts an **update** (`broadcastStatusCreatedToAudience` → `status.update`, public/home/lists) whose payload carries the cached copies, so every client swaps the images in place (`mergeStatusUpdate` keeps the viewer fields). Cards only attach when their image is cached or failed. Statuses with no remote media are unaffected, and the flag is cleared when the cache is disabled. A safety valve (`MEDIA_CACHE_MAX_HOLD_MINUTES`, 30 min, 0 disables) releases older flags anyway so a degraded cache still refreshes the clients.
- Config (all env vars, cache ON by default): `MEDIA_CACHE_ENABLED`, `MEDIA_CACHE_DAYS` (7, attachments), `MEDIA_CACHE_PROFILE_DAYS` (30, profiles of accounts with a local follow relation are kept), `MEDIA_CACHE_MAX_BYTES` (10 GiB, least served evicted first), `MEDIA_CACHE_MAX_OBJECT_BYTES` (40 MB), `MEDIA_CACHE_FETCH_BATCH` (20/tick — a guardrail: a queue fed by re-queued evicted URLs once meant ~70k R2 writes/day), `MEDIA_CACHE_USER_AGENTS` (overrides the whole list; by default the bot UA — built from `INSTANCE_VERSION`/`INSTANCE_URL` — is tried first, then browser UAs; non-media types, SVG and oversized bodies are rejected).
- **Serving**: `/api/media/…` is intercepted in `src/worker.ts` **before** vinext and served by `lib/media/serve.ts` (the route stays as a fallback when the worker does not intercept). The framework appends `Vary: rsc, next-router-state-tree, …` to app responses and Cloudflare only honours `Vary: Accept-Encoding` when caching, so with the framework header the CDN skipped the cache and every video range request streamed R2 → Worker → client; browsers cancel buffered streams on purpose, which floods the logs with "Network connection lost" plus the runtime's hung-request cancellation. Range rules: single range → 206, unsatisfiable → 416, **multi-range/malformed → 200 with the whole body** (RFC 9110 lets a server ignore `Range`; the old 416 broke Safari-style probes), HEAD/304/416 answer from `R2.head` without touching the body, and CORS allows `Range` and exposes `Content-Range`/`Accept-Ranges` so cross-origin clients can seek.
- Hooks: `enqueueMediaCache` in `handleCreate`/`saveObjectAttachments`/`storeObjectAttachments`/remote featured items, and in `upsertRemoteActor` for avatars/headers — **only when the URL is new or changed** (`enqueueNewProfileImages` reads the stored actor row before the upsert): queueing on every actor update re-downloaded each evicted avatar on the actor's next activity (~30k R2 PUTs/day on cf-ap). **Nothing may re-queue an evicted/expired URL**: the cache is bounded and evicts least-served entries first, so a backfill that re-queues what was just evicted turns the cache into a re-download loop — media is queued where it is ingested (attachments and card images on create, profiles on first sight or change) and `backfillMediaCache` only seeds followed profiles plus the D1-only stale-reference healing. Cron runs `maintainMediaCache` (expiry + byte-budget eviction + orphan cleanup) FIRST, then drains the queue (`processMediaCacheQueue`), releases held statuses, and leaves the optional `backfillMediaCache` and the expensive one-shot reference repair LAST (the repair is throttled to one attempt every 10 min and walks `attachments` in 20k-rowid windows with its cursor in `instance_settings`) — a slow optional step must never delay the queue drain. Expiry, eviction and purge **restore every reference before deleting the row** (`resetMediaCacheReferences`: `attachments.url = remote_url`, `actors.*_cache_url = NULL`, `preview_cards.image_cache_url`/`card_json` back to the origin image) — deleting the R2 copy while references kept pointing at `/api/media/...` produced dead avatars/attachments (849 on cf-ap). The reset matches **by the cached URL as well as by the origin URL**: an account that replaced its avatar keeps the old cached copy (`upsertRemoteActor` preserves `avatar_cache_url`) until the new one is fetched, so its row's origin no longer equals the entry's `source_url` and an origin-only reset left the reference dangling when the entry was evicted (4 profiles + 1 attachment on cf-ap, Oct 2026 — `scripts/upgrade-schema.mjs` clears the repair marker so the cron pass, which matches by `cached_url`, heals existing instances). A marker-guarded one-shot cron repair (`repairMediaCacheReferences`, `media_cache_refs_repaired`) heals references the old code already broke — its object/actor scans are forced with `INDEXED BY` (`idx_objects_card_id`, `idx_actors_avatar_cache`/`idx_actors_header_cache`): without the hint the planner full-scanned `objects` (227k rows, ~8 s) on every attempt; run `node scripts/upgrade-schema.mjs` so the `media_cache.cached_url` / `attachments.remote_url` / `actors.avatar_url` / `header_url` indexes exist first. Resetting `attachments.url` back to the origin can collide with the unique `(object_id, url)` index when one object holds two rows for the same source (one already at the origin, one stale cached): the apply/reset/repair paths dedupe those rows (keep the origin-serving one) before rewriting — the old plain UPDATE failed with `SQLITE_CONSTRAINT_UNIQUE` and aborted maintenance. Maintenance also drops entries whose owner is gone (deleted status/attachment, unlinked preview card, deleted or replaced actor avatar) — an avatar of a live account is never touched, it only goes when the actor row does. The orphan sweep probes only indexed columns (`idx_attachments_remote_url`/`idx_attachments_url`, `idx_actors_avatar_url`/`idx_actors_header_url`, `idx_preview_cards_image`): an `OR` over two non-indexed columns full-scanned `attachments` per cache entry and tripped D1's CPU limit (the admin media_cache GET started failing). Eviction runs **only when the cache is over budget** (under it, the retention window is the only thing that removes entries) and **recycles cold-and-quiet entries first** (`MEDIA_CACHE_COLD_DAYS` = 3 without a serve and at most `MEDIA_CACHE_COLD_MAX_HITS` = 5 serves, ordered by `last_hit_at`, index `idx_media_cache_cold(status, last_hit_at)`) — a barely used file nobody asked for in a while must not outlive the fresh media it competes with, while a file with many serves keeps its place — and then falls back to the **least served first** (`hits ASC, fetched_at ASC`, index `idx_media_cache_evict`), with a 500 MB/tick byte budget — enough to drain a large overage — and `MEDIA_CACHE_MIN_ENTRIES` (20) is a floor: the cache is never wiped automatically (only the full-admin purge wipes). `media_cache.hits`/`hits_at` count how many times an entry was **served**: the media serve path (`src/worker.ts` interception and `app/api/media/[...key]/route.ts`) records hits in memory (`lib/media/hits.ts`) and flushes them as one batched UPDATE (interval 60 s or 200 keys), so the hot path does no per-request D1 I/O and a recycled isolate only loses a few counts; the counter restarts when an entry is served again after the attachment retention (`MEDIA_CACHE_DAYS`; `mediaHitWindowDays`) without a serve, so a file that went cold and came back is judged by its recent use instead of a lifetime total — the cache protects what clients actually request without permanently reserving budget. `last_hit_at` slides the time-based expiry the same way: an attachment still being served is not deleted at `MEDIA_CACHE_DAYS` only to be re-downloaded, and once it goes cold for a full window it expires normally. Counts are only recorded for served bodies (200/206). The byte total is `SUM(media_cache.size)` in D1 (never a KV counter: concurrent updates lost writes); downloads stream straight into R2 with a size-capped `TransformStream` and a bounded pool (8 concurrent) — buffering 50 bodies at once (up to `MEDIA_CACHE_MAX_OBJECT_BYTES` each) exceeded the Worker memory limit; the auto-delete stage is capped at 500 objects/tick because `objects.raw` is a full AP document. Fetching runs as a **rolling window**: `maintainMediaCache` evicts the least served entries every tick and only a runaway overage (>2× `MEDIA_CACHE_MAX_BYTES`) pauses fetching, so the queue never stalls at the (normal) saturated steady state; backfill pauses while over budget. The queue batch (`listMediaCacheQueue`) is 70% newest-first (a just-ingested status must enter timelines quickly) and 30% oldest-first: under sustained arrivals pure newest-first starved the backlog forever — the avatar of a held status was never fetched, so the status waited for the 30-minute safety valve while its own image was already in R2 (cf-ap, Oct 2026). The admin GET reports `top_served` (top 10 entries by `hits`, aged by the attachment retention) so an operator can see what the budget protects. Admin API: `GET / POST / DELETE /api/v1/admin/media_cache` (`POST` runs `enforceMediaCacheBudget` until under the limit, bounded to 60 s, and reports the counts). The admin UI lives at `/admin/media_cache` (nav entry only shown when the cache is enabled, checked against `GET /api/v1/admin/media_cache`): it shows the stats and effective config, lists `top_served` as **plain links, never images or `next/link`** — rendering a preview would itself count as a serve and protect the entry — and gives full admins the purge button (`DELETE`, confirm dialog, audit-logged). `mediaCacheLimitsFrom(instanceLimits)` is the only bridge between `resolveLimits()` (fields prefixed `mediaCache*`) and the cache module: the cron once passed the raw limits object, every field fell back to defaults (10 GiB) and `MEDIA_CACHE_MAX_BYTES` was silently ignored. `MEDIA_CACHE_MIN_ENTRIES=0` is accepted (uses `nonNegativeNum`).

### Link previews (Mastodon PreviewCard)

- A status with a link gets a Mastodon-style preview card: the **first external URL** (hashtag/mention links and own-instance links skipped) is queued in `link_preview_queue` and crawled by the cron (`lib/link-preview.ts`), like Mastodon's `FetchLinkCardService`. Statuses with media or a quote are skipped.
- The crawl tries **oEmbed first** (JSON discovery via `<link type="application/json+oembed">`; `rich` is rejected like Mastodon) and falls back to **OpenGraph/Twitter Card/JSON-LD** (`og:title`/`og:description`/`og:image`/`og:site_name`/`canonical`/`article:published_time`); `twitter:player` becomes a sanitized `<iframe>` (`type=video`, https-only, scripts dropped). Outbound requests use `fetchWithUserAgents` (`lib/media/fetch.ts`) — the **same user agents and fallback** as the media cache — and `safeFetch` (SSRF) for every hop.
- Cards live in `preview_cards`, keyed by the URL as posted, **shared by every status** linking to it and refreshed after `LINK_PREVIEW_DAYS`. Unreachable/no-metadata URLs are negative cached (`status='failed'`, 7 days).
- Each status stores a snapshot (`objects.card_id`/`objects.card_json`) so `serializeStatus` emits `card` with **no extra queries** anywhere (timelines, notifications, streaming re-serializations, quote). Editing a status clears/re-crawls the card only when its first link changed.
- With the media cache enabled the preview image is queued there too (`media_cache.target_type = 'card'`); when it becomes ready, `preview_cards.image_cache_url` and every `objects.card_json` are updated in place (`json_set`). Env: `LINK_PREVIEW_ENABLED`, `LINK_PREVIEW_FETCH_BATCH`, `LINK_PREVIEW_DAYS`, `LINK_PREVIEW_MAX_BYTES`; `linkPreviewLimitsFrom(instanceLimits)` is the typechecked bridge from `resolveLimits()`.
- When the card is attached the cron broadcasts `status.update` (public channels, home feeds of the author's local followers — including the author — and every list containing the author, via `broadcastStatusRefresh`) so it appears **without a manual refresh**; the client merge (`mergeStatusUpdate`) preserves viewer-specific fields (`favourited`, `reblogged`, `bookmarked`, `muted`, `pinned`, `filtered`) because the shared payload cannot know them. The status detail page also handles `status.update`. Include the poll in the refresh payload: a poll status with a link would otherwise lose its options on update.
- **Every object-storing path must queue the crawl** (`maybeEnqueueLinkPreview`): `persistRemoteNote` (boosted/embedded objects), the Update branch that creates a new status, the Like/Flag evidence caches and `fetchAndCacheRemoteActorFeatured` (remote pins) are **not** `handleCreate`, and missing them left boosts and pinned posts card-less (`lib/activitypub/remote.ts` paths all enqueue). Objects already stored are skipped by `handleCreate`, so a status first cached by those paths never got a second chance.
- **YouTube builds its card from the URL** (`lib/youtube.ts`): `youTubeVideoId` recognises watch/youtu.be/shorts/embed/live/music and rejects channel paths. The crawler applies `applyYouTubeFallback` (CDN thumbnail + nocookie player) not only when the page yields metadata but also when the fetch fails (403/consent wall) or the page has none — using the video id plus the **direct oEmbed endpoint** (`www.youtube.com/oembed?url=…`, reachable from datacenter IPs when the watch page is not). Placeholder titles ("- YouTube") are dropped so the card shows the player instead of a fake name.
- **Instagram builds its card from the URL** (`instagramShortcode`/`applyInstagramFallback` in `lib/link-preview.ts`): Instagram killed public oEmbed and answers a login wall (or 429) to datacenter fetches, so the crawler keeps whatever OG metadata it got — or none — and always exposes the public `/embed` player as `embed_url` with `type: video`; the web UI frames `video` cards, so reels play in the lightbox (photos show inside the same embed). Existing cards were repaired in production from their `source_url` (card row + every `objects.card_json` snapshot).
- The orphan sweep (`cleanupOrphanPreviewCards`) collects cards no status points at, but **never a live negative cache** (`status='failed'` with a future `next_attempt_at`): unattached by definition, deleting them re-crawled dead origins on every new status linking to them.
- **Own status permalinks** are built straight from the database (a Worker fetching its own hostname times out with HTTP 522): the card carries the **author name** as title and the status text as description, uses the status' first **image attachment** as its image (never the author avatar, which painted a stretched banner) and keeps the `/embed/<id>` iframe **only in `html`** (API clients) — `embed_url` stays empty so the web UI never opens a status embed in the 16/9 lightbox (a short status reads as an empty box).
- The web UI (`components/StatusCard.tsx`) renders the card image (blurred while the status is sensitive, same reveal button as media) + provider/title/description, linking out with `rel="nofollow noopener noreferrer"`. In-place playback goes through `playableCardEmbedUrl`: only provider **players** are framed — YouTube always (whatever `type` the stored snapshot carries) plus cards the crawler typed as `video` (Vimeo/PeerTube/Dailymotion). `rich` embeds are pages, not media (WordPress post embeds, Mastodon status embeds): they keep the plain link card, because framing one in the 16/9 lightbox reads as an empty box. `card.html` is still exposed for Mastodon clients.

### Security invariants (audited)

- **Actor trust**: never cache a fetched actor document whose `id` differs from the URL fetched — call `upsertRemoteActor(db, doc, expectedId)` at every fetch site. Server-side fetch helpers must check before upserting.
- **Object attribution**: remote objects may only be stored when `attributedTo` shares the object IRI's host and is not a local actor (`handleCreate`, `handleLike`, `handleFlag`, `fetchAndCacheRemoteStatus`, `persistRemoteNote`).
- **Visibility**: every route reading an object by id gates with `canViewStatus(obj, viewerId, isAcceptedFollower(db, viewerId, obj.actorId))` — including source/history/translate/favourited_by/reblogged_by/pin/account statuses. `getFollow` ignores state and must never be used for visibility. The rule mirrors Mastodon's `StatusPolicy#show?`: a **followers-only** post is visible to the author, its followers **and the accounts it mentions** (`mention_exists?`) — a followers-only post is delivered to the mentioned accounts, so the mention notification they receive must open (`test/status-visibility.workers.test.ts`); without that third case the notification linked to a 404.
- **Registration**: always `email_verified = 0` + confirmation email (web and API); the API still returns a Mastodon-shaped token but it is unusable until confirmed. Local actor ids come from `getBaseUrl(env)`, never the request Host.
- **Canonical email (anti-abuse)**: `lib/canonical-email.ts` collapses `user+tag@domain` and dotted local parts for EVERY domain (googlemail≡gmail). `actors.canonical_email_hash` stores sha256(canonical), `canonical_email_blocks` denies a mailbox, and the registration flow rejects duplicates of an existing mailbox, auto-blocks after 3 attempts from the same mailbox (24h KV window) and audits it (`registration_blocked`). Admin API: `/api/v1/admin/canonical_email_blocks` (full admin).
- **OAuth**: authorization codes require matching `client_id` + `redirect_uri` and PKCE whenever a challenge was issued; scopes are clamped to the app's registered scopes; an empty scope is not full access; a session cookie is only set for same-origin logins. `POST /oauth/token` supports `authorization_code`, `password`, `client_credentials` (app-level: **no actor**, read-only, 1 h) and `refresh_token` (rotates the access token **in place** with `refreshOAuthTokenAccessToken`, keeping the refresh token and the granted scope like Mastodon/Doorkeeper, and re-checks the account: suspended/unconfirmed/pending-approval cannot refresh). Every user-facing grant sets `actor_id`; only `client_credentials` leaves it NULL — rows without an actor are app tokens, never a user session. Crawler-registered apps and their app-level tokens are pruned by the `prune_unused_oauth_apps` INSERT trigger and the cron (`cleanupUnusedOAuthApps`: app tokens expired or >24 h, apps >1 h without a user token or a live app token).
- **Admin roles**: `requireFullAdmin` guards role changes, instance settings, federation rules, audit-log wipes and instance mutations; never demote/delete the last admin. Account actions (suspend/silence/approve/reject) go through `accountActionGuard` (`lib/admin/account-guards.ts`): reserved actor immutable, no self-actions, admin targets need a full admin, and last-administrator access can't be removed (`countUsableAdmins` ignores the credential-less Guardian actor). **Deleting an account is a full administrator action** (`DELETE /api/v1/admin/accounts/:id` reads `getAdminRole` directly): a moderator suspends, silences, approves or rejects, but deletion — irreversible, it takes the posts, followers and uploads with it — is refused with a 403 + `admin_account_delete_admin_only`, and `/admin/accounts` only renders the delete, promote/demote and memorialize buttons for administrators (the moderation buttons stay). Privileged mutations (roles, reports, domain blocks, settings, announcements, instances, log edits) write `moderation_log`.
- **The reserved instance actor (the Guardian) is immutable**: `accountActionGuard` refuses every admin action on it (422 + `admin_error_reserved_account`), and the moderation engine refuses it too — `suspendAccount`, `warnAccount`, `silenceAccount` and `rejectAccount` change nothing and record a `no_action` entry with the attempted action (`details.attempted`), because an inbound report or a patrol verdict must not be able to turn the instance's own bot off. The account patrol's candidate query excludes reserved rows, the registration sweep's queries do too (it already missed the Guardian: no email, verified) and the expiration sweep exempts it. **Restorations stay possible** (`restores: true` on the unsuspend/unsilence routes): a state that should never have been applied must remain repairable, and the engine's `unsuspendAccount`/`unsilenceAccount` deliberately have no reserved check. `ensureGuardianActor` self-heals the row (`role = 'admin', reserved = 1`) for an instance whose Guardian predates the flag — without it the bot would be a normal admin account anyone could suspend or demote. `/admin/accounts` shows it as `admin_status_reserved` and hides its action buttons.
- **Moderation notices**: `notifyAccountOwner` (lib/moderation/actions.ts) emails the owner (local accounts with an email on file only) on warn/suspend/silence/remove, report rejection and status deletion through the bilingual `sendModerationNoticeEmail` template; admin account deletion calls it **before** the actor row disappears and records `emailSent`/`emailTo` in `moderation_log`.
- **Guardian AI tiers (clef)**: first-line screening runs **`clef-flash`** on every status (`screenContent`: an `unsafe` noul plus a `category` choice — categories ≥ 0.25 are reported and drive the severity gating in `screenStatus`), while the reasoning decisions (report, content, account, registration) run the full **`clef`** through `decide()` (`lib/moderation/ai.ts`): the action comes from the `action` choice question, the confidence from the chosen option's probability (≥ 0.7 high, ≥ 0.45 medium — suspension and registration auto-approval require high) and the `reason` is synthesized from the answered yes/no signals (`signalsReason`, Spanish labels). Clef has **no system prompt**: the policy lives in the question instructions/criteria (`lib/moderation/prompts.ts`), the evaluated data travels as a sanitized JSON `state`, and every question repeats that the state is untrusted content, never instructions. A failed call is retried once and then returns null (heuristics take over), and the chosen action is always validated against the allowed set.
- **The Guardian is also a Cloudflare Agent** (`agents` + `@cloudflare/ai-chat`, `lib/guardian/`): an admin can talk to it in `/admin/guardian` and it answers **grounded in its tools**, never from the model's memory. `GuardianAgentDO` (`lib/guardian/agent.ts`) is a Durable Object — binding `GuardianAgent` (the binding name is what the SDK kebab-cases into the `/agents/guardian-agent/:instance` URL) + migration `v2` (`new_sqlite_classes`, never extend `v1`: migrations are immutable once deployed), exported by `src/worker.ts` **and** `test/worker.ts` under the `class_name` wrangler instantiates — that `AIChatAgent` gives durable chat history (SQLite, bounded by `maxPersistedMessages`), resumable streaming and synced state. `routeGuardianAgent` (`lib/guardian/routing.ts`) serves `/agents/guardian-agent/:instance` from the worker **before** vinext and gates it to a **full administrator** (the agent reads every report and can suspend; a moderator gets a 403, an anonymous caller a 401 — the nav entry is hidden from moderators too, and the panel shows the notice if the socket is refused). The tools (`lib/guardian/tools.ts`, built from the bindings so they are testable without a DO) are the only source of truth: reads (`instance_overview` via `getGuardianSnapshot`, `list_reports`, `get_account`, `search_statuses`, `recent_decisions`) and **`needsApproval` mutations** (`suspend_account`, `unsuspend_account`, `silence_account`, `warn_account`, `delete_status`, `review_report`) — the model proposes, a human approves in the chat, and the approved action goes through the moderation engine with `source: "user"`, `model: "guardian-agent"`, so it is audited in `moderation_log` exactly like a decision taken from the admin UI. `review_report` re-runs the Guardian's own `evaluateReportWithAI` pipeline on an open ticket. The chat runs on Workers AI through the same `AI` binding (`workers-ai-provider`, tool calling required); the model id lives in the agent state (`setModel`), defaulting to `@cf/zai-org/glm-4.7-flash`, and the agent does **not** charge the automated Guardian's daily AI budget — it only runs when an administrator asks. State (`snapshot`) is refreshed by the `refreshSnapshot` callable and reaches every connected panel over the agent's WebSocket; `onRequest` answers a plain JSON view of the same snapshot (what the test suite uses). **No decorator syntax may reach a bundle**: the SDK marks RPC methods with a standard decorator, but Vite 8 transforms with Oxc (which keeps decorators at any target) and workerd's V8 cannot parse them — a decorated agent class took the whole deployed Worker down at startup (`SyntaxError: Invalid or unexpected token`, caught by `vite preview`). `exposeMethod` (`lib/guardian/agent.ts`) therefore registers the callable metadata on the prototype methods (the SDK's `callable()` is only a WeakMap registrar and `decoratedMethods` walks the prototype chain), and ESLint's `no-restricted-syntax` forbids `Decorator` everywhere so it cannot come back. `test/guardian-agent.workers.test.ts` asserts the two callables are registered, the administrator-only gate, the snapshot and the tools (including that an approved `suspend_account` really suspends and audits as `guardian-agent`).
- **The Guardian learns from every suspension** (`lib/moderation/learn.ts`): `learnFromSuspension` embeds the offending content the caller already has plus a sample of the account's own posts and its profile (`account:<actorId>`, `action: suspend`) into the vector memory, and **every** suspension path calls it — `suspendAccount` (the Guardian's content/account/report/duplicate-spam decisions; it runs **before** the posts are nulled, which is the only reason the account's own text can still be read), the moderator route behind `/admin/accounts` and the registration sweep (capped per run: one wave repeats one pattern and the memory must not flood). A human or rule suspension carries no model probability, so it is stored as a confirmed decision instead of being dropped by the "no low confidence" rule, and the audit entry records the outcome (`details.learned`). The lessons are consumed by the content screening (`vectorPreScreen`) and at sign-up: a profile that is a near duplicate of a previously rejected registration is refused outright (`AUTO_ACTION_THRESHOLD`, `registration`-kind matches only) while a looser match reaches the model as `similar_confirmed_abuse` precedent. Lifting a suspension is a correction — `forgetSuspension` deletes the vector (`details.forgotten`) — or a mistaken suspension would keep auto-actioning whatever resembles it. A domain block deliberately does **not** teach: it is an instance-level policy decision, not per-account confirmed abuse.
- **Every registration is audited** (`app/api/v1/accounts/route.ts`): the sign-up writes one `moderation_log` entry (`registration_reviewed`, with `details.verdict` = `allow` / `approve` / `reject` / `unreviewed`, the deterministic `flags`, the vector match and `pendingApproval`) whether the reasoning model reviewed the profile or the heuristics admitted it — a flagged registration whose review is unavailable (no AI binding, budget spent, model returned nothing) is recorded as `unreviewed` instead of vanishing. The pre-creation blocks keep their `registration_blocked` entry. The model's **approve verdict changes no state**: it must never set `email_verified` (only the confirmation link does — the old `approveAccount` helper did, so a flagged sign-up ended up active without confirming its mailbox, and the helper is gone), and a rejection deletes the account through `rejectAccount` with `verdict: reject` in its details. `recordModeration` reports a failed write to the console: a silent gap in the audit trail is worse than the failed action.
- **Captcha (Turnstile)**: `enforceTurnstilePolicy` requires a valid token on registration, web login and password recovery **whenever `TURNSTILE_SECRET` is configured** (it skips only when no secret is set, and never treats a missing token as verified). The old `if (turnstileToken) verify(...)` check was a trivial bypass: omitting `cf-turnstile-response` skipped the challenge. The login password grant skips the captcha only for a registered OAuth app with matching `client_id`+`client_secret` (API clients); failed passwords increment an IP-independent per-account lockout (10/15 min, cleared on success). `expectedHostname` always comes from `getBaseUrl(env)`, never the request Host.
- **OAuth scopes**: `read` is enforced on GET/HEAD and `write` on mutations; `push` on push subscriptions. Scopes are clamped to the app's registered scopes (`clampScope`) on every issuance path — registration included — and an empty scope is not full access. Promoting moves one step (user → moderator → admin) and promoting an admin is a no-op — the old promote silently downgraded admins. Role changes are written to `moderation_log` (`promoted`/`demoted`) and the reserved instance actor's role is immutable. The authorization code carries the app's **`client_id`** (`oauth_code:` KV payload): the token exchange compares that, never the internal `appId` — comparing the row id rejected every app with `invalid_client` and clamped its scopes to `read`.
- **Streaming**: both Durable Objects use the **WebSocket Hibernation API** (`acceptWebSocket` + `serializeAttachment` for per-socket state + `getWebSockets`/tags + `webSocketMessage`/`Close`/`Error` + a storage alarm for the anonymous TTL), so idle sockets cost no duration; the keep-alive the browser sends (`"ping"` every 25s — the WebSocket API cannot send protocol ping frames, which the runtime answers for free) is answered by `setWebSocketAutoResponse("ping", "pong")` in the constructor: waking on every keep-alive would defeat hibernation and bill the object for staying alive. `CallSignalingDO` implements `webSocketError` too (it notifies the peer like a close). List channels are owner-checked in the worker (dynamic re-subscribe limited to the socket's initial list) and only public/unlisted statuses are broadcast to them; streaming tokens honor the same suspension/verification gates as REST. **The home fan-out mirrors the REST filters**: `eligibleLocalRecipients` (lib/streaming/broadcast.ts) is the single gate — a local follower who blocked the author (or its domain) or, for a reply, the parent's author gets no live event (`broadcastToAuthorAudience`, `handleCreate`, `broadcastNewBoost`, the local status POST/PUT routes and the scheduled-publish cron all go through it, and streamed serializations pass `inReplyToAccountId`). The shared public/hashtag channels cannot be filtered per viewer, so the web client fetches the viewer's blocks + domain blocks once per session (`lib/streaming/blocked-accounts.ts`) and `useNewStatusesBuffer` drops streamed statuses from blocked accounts or replying to them (the caches are invalidated on block/unblock).
- **Profile-field verification** is HTTPS-only and KV-throttled: `verifyAccountFields` skips plain-http field values silently, remote accounts are retried at most every 6h and re-verified after 30 days (badge revocation). An `https` field whose page redirects to plain HTTP is blocked by `safeFetch` (`[federation] Blocked outbound request …` in the logs) — expected, not an attack. Our own actor emits field values as `<a href="URL" rel="me">URL</a>` (`fieldValueForVerification`): Mastodon's `Account::Field#extract_url_from_html` only accepts a single anchor whose `href` equals its text, so a plain URL is never verified remotely.
- **Browser-facing API errors**: return a stable `error_code` (i18n key) next to the English `error`/`error_description`; the web forms translate it with the existing client i18n (`translateKey` in `lib/i18n.tsx`). Never ship untranslated user-facing strings.
- **Remote HTML** goes through `sanitizeFediverseHtml` (control chars stripped, http(s)-only media `src`); remote bodies are size-capped (2 MB) before parsing.

## Code conventions

- **Path alias** `@/*` → repo root. Always import with `@/`.
- **API routes**: exported async `GET`/`POST`/… typed `(request: NextRequest, { params }: { params: Promise<{ id: string }> })`. Use `json()`/`notFound()`/`unauthorized()`/`badRequest()` from `@/lib/cf`. Form-encoded bodies come from clients built against Rails: parse them with `formDataToBody`/`readRequestBody` (`lib/request-body.ts`), which reproduce Rails' array/nested conventions (`media_ids[]`, `poll[options][]`, `push[data][alerts][follow]`). `Object.fromEntries` kept the brackets verbatim, so `body.media_ids` was undefined and a status published by Tusky came out **without media**; a bare `media_ids=<id>` (no brackets) is accepted too (`normalizeMediaIds` in the statuses routes).
- **Streaming**: components never open a raw WebSocket — `lib/streaming/use-timeline-stream.ts` is a shared, ref-counted manager: one socket per (stream + extra params) reused by every listener, kept alive 30s after the last unmount so tab switches reconnect nothing, and `user:notification` is served from the `user` socket (home channel already forwards notifications), filtered to notifications only. Non-timeline events for one local actor go through the generic `broadcastEvent(ns, actorId, type, data)` (profile pages listen for `relationship`, the call overlay for `call`) — add an event type, never another helper. **Account state changes** (`account.updated`, `{ id, suspended }`) go through `broadcastAccountUpdate` (`lib/streaming/broadcast.ts`) on the public channels, the home feeds of the account's local followers and its list channels: a suspension hides the account's posts server-side (every timeline query filters `suspended = 1`) but a client with a cached feed keeps rendering them until the event arrives — the case that matters most for a **remote** account, which gets no `Update{Actor}` broadcast at all (a local one is covered by `broadcastActorState` too). `handleStatusStreamEvent` drops everything the account authored (and the boosts wrapping its posts) and removes those ids from `seenIds`, so an unsuspension can bring them back on the next refetch. Admin tables that wait on a remote answer (relays) poll instead of depending on a socket.
- **Stream payloads and interaction responses are full statuses**: the client merge (`mergeStatusUpdate`) replaces everything except the viewer fields (`favourited`…), so every `status.update`/boost payload **and every interaction response** (favourite, reblog, bookmark, pin, mute, edit, delete) must carry the complete context — attachments, custom emojis, poll, quote, parent author — through `serializeStatusForStream` (`lib/streaming/serialize.ts`), with the viewer state loaded by `loadViewerStatusState` (so unfavouriting a bookmarked post doesn't clear its bookmark icon). A partial payload silently wipes what is on screen: the boost refresh serialized without attachments, so every cached status lost its images the moment it was boosted, and interaction routes serialized without `quote`, so favouriting a quote made its card disappear. Held statuses (`media_pending = 1`) are never streamed — the cron announces them once their media is in R2 — and boosts fan out to the booster's local followers through `broadcastNewBoostToFollowers` (`lib/streaming/boost.ts`), used by both `handleAnnounce` and the local reblog route.
- **Federated images render as plain `<img>`**: `next.config.ts` sets `images: { unoptimized: true }` because vinext routes `next/image` local paths through `/_next/image`, whose asset resolver only serves the static client bundle — every `/api/media/...` image 404'd there (and the shim's remote branch validates private-IP hosts, which blocks `localhost` in dev). `MediaGrid` and `LinkPreview` also swap an image that failed to load (dead origin, evicted cache entry) for a labelled placeholder (`media_unavailable`).
- **The audio waveform is a live spectrum**: `lib/audio-visualizer.ts` + `AudioWaveform` (`components/MediaPlayer.tsx`) drive the bars from a real `AnalyserNode` while playing and restore the static seek pattern on pause. Constraints: one shared `AudioContext` per document, one source/analyser per element, and **same-origin sources only** — routing a cross-origin element through Web Audio without CORS silences it per spec, so remote origin URLs (uncached media) keep the static bars. The animation loop writes `transform`/`background` directly and the component is memoised, so playback costs zero React re-renders; `loadViewerStatusState`-style progress updates never touch the bars.
- **Search inputs**: debounce (400 ms) and make every run supersede the previous one (`AbortController` + sequence guard) with a `try/finally` that always clears the loading flag — a slow response for an earlier prefix must never overwrite the current query's results nor leave the "searching" state stuck, and clearing the field cancels the in-flight request and returns to the default view (Explore).
- **Timelines**: client feeds share `useTimelineCache` + `lib/streaming/timeline-cache.ts`. Always merge with `mergeTimelineItems` (dedup + newest-first by `created_at`, the same field the server orders by) — never prepend streamed statuses blindly (a late federated post would jump to the top). A failed/empty page must never replace cached items, and `seenIds` is always derived from the visible items. Timeline `fetchPage` throws on `!res.ok`; the hook keeps the current feed and retries. **Every cache write goes through `setTimelineCache`, which caps a feed at `timelineCacheMaxItems`** (default 1000, newest first — and a missing anchor falls back to the remembered offset). **Pagination follows a cursor, never the feed's last item** (`TimelineCacheEntry.cursor`, persisted and restored): when a catch-up merges a page the cache never saw, the statuses in between were never downloaded, so the cursor becomes the fetched page's oldest and scrolling continues there — paginating from the cached tail jumped straight from the new posts into yesterday's, skipping the gap. While the reader is at the top the catch-up also **fills that gap eagerly**, bounded to `MAX_GAP_PAGES` (5) extra pages, so a normal absence renders one continuous feed; beyond the bound the rest is left to the cursor. A page of already-known statuses is the sentinel reaching the restored cache (a prefix of the feed), not the end — pagination stops only on a page that makes no progress at all (same cursor, nothing new) or an empty one. `lib/__tests__/use-timeline-cache.test.tsx` pins all of it (gap-filled order, the bound, the cursor surviving in the cache) — **the write also evicts the least recently written feeds beyond `TIMELINE_CACHE_MAX_ENTRIES`** (12): a feed can be scrolled forever, and caching every page made a restore re-render thousands of cards. **Streamed statuses go through `useNewStatusesBuffer`** (`lib/streaming/use-new-statuses.ts`): at the top of the feed they merge straight in, but once the reader has scrolled away (`NEW_STATUSES_TOP_OFFSET`) they queue behind `NewStatusesPill` ("N new statuses", `timeline_new_statuses`/`_one`) and only appear when the pill is pressed (which also scrolls to the top) or when the reader scrolls back to the top — the feed must never jump under their finger. `delete`/`status.update` events always apply immediately. A **background refetch defers too**: `useTimelineCache` hands the statuses it fetched while the reader was scrolled away to `onDeferredItems`, and the pages queue them behind the same pill (`queueItems`) — they stay out of the feed **and** out of the cache, so coming back from a status detail restores the exact position instead of shifting the timeline. **Counters are never guessed client-side**: interaction handlers copy `favourited`/`favourites_count` (or reblogs) from the status the action's own route returns, and posting a reply re-reads the parent instead of a local `+1` — the routes already increment the row and broadcast the parent with the refreshed values, so a local bump raced with that merge and counted twice (fav 2, reply 2 with one action). **`StatusCard` is memoised** and every feed must keep its props stable: handler props via `useCallback` (never inline arrows), and lists that derive their statuses or live next to a composer wrapped in `useMemo`/`memo` (`HomeTimeline` on the home, the conversation and E2EE lists, the list-detail timeline) — typing in a composer must never re-render the feed, or typing gets slower as the timeline grows. **A feed whose membership is filtered server-side must filter in the query, not in the route**: the notifications tabs (All / Mentions, `/notifications`) pass `types[]`/`exclude_types[]` down to `getNotifications`, which applies them in SQL (`idx_notif_target_created(target_account_id, created_at DESC, type)` gives the ordered scan and evaluates the type filter from the index). Filtering the fetched page in the route returned short pages — the Mentions tab held only the mentions that happened to fall inside the first page — and the client's `hasMore` (`items.length >= pageSize`) stopped paginating; each tab is its own cache entry (`notifications`, `notifications:mentions`) and the stream refetch follows the active tab — it **merges the first page** (`catchUp`) instead of fetching one notification: the event payload is `{}`, so fetching `?limit=1` added only the newest one, and a burst (or an event missed while the tab was hidden) left the sidebar badge counting more than the list showed until a reload. The page also reconciles on `visibilitychange`, because the badge keeps polling in a background tab while stream events are missed there. The Mentions tab carries `direct`/`encrypted` too: Mastodon delivers DMs as mention notifications, so its Mentions tab shows them.
- **Anonymous timeline access**: the `anonymous_timelines` instance setting (`public` default / `public_local` / `none`, admin → Settings, `lib/anonymous-timelines.ts`) decides what visitors without a session may read. Enforced in the REST route (`/api/v1/timelines/public`, the `local=true` view included) **and** in the streaming worker (`public`, `public:local` — otherwise a WebSocket bypasses the REST gate); the UI (local tab, sidebar entry, sign-in state) reads it from `/api/v1/instance` via `useAnonymousTimelineAccess`, and the admin settings PUT drops the cached instance payload so a change applies immediately. Any new anonymous timeline surface must check it.
- **Auth**: `getAuthenticatedActor(request, env.DB)` from `@/lib/auth` (cookie `auth_token` or Bearer; client `getToken()` from `@/lib/client-api`). It rejects suspended, **email-unconfirmed** and pending-approval local accounts. Mutating requests require the `write` scope (`read`-only tokens are rejected). Self-service registration (`POST /api/v1/accounts`) always sends the confirmation email and creates the account with `email_verified = 0` — the presence of a Turnstile token must never auto-verify (API clients skip the captcha, not the email). API registrations still receive a token (Mastodon shape) but it is unusable until confirmed. Admin: `requireAdmin(request, env)` from `@/lib/admin-auth` (role + optional `ADMIN_TOKEN`). Suspended/deleted sessions are bounced to the landing page: `GET /api/auth/status` returns a `reason` (`suspended`/`deleted`/`invalid`/`unverified`/`pending`) and the root-layout `SessionGuard` (`components/SessionGuard.tsx`) clears the token and lands on `/` — silenced (limited) accounts keep their session (Mastodon parity). The password grant rejects suspended/pending-approval accounts (`login_error_suspended`/`login_error_pending_approval`) instead of issuing a token every API call would reject.
- **i18n**: 10 locale files in `lib/locales/`. `t` from `useLocale()` is a Proxy — use `t.some_key`; interpolate with `.replace("{var}", value)`. **Every key must exist in all 10 locales with identical key sets** — never hardcode user-facing strings.
- **Brand**: read `useInstanceTitle()` / `INSTANCE_TITLE`; metadata comes from `generateMetadata()` in `app/layout.tsx` and the PWA manifest from `app/manifest.webmanifest/route.ts`. Don't hardcode the instance name in UI.
- **Limits**: read `resolveLimits(env)` (`lib/constants.ts`) instead of hardcoding page sizes/char limits; new limits get a constant, an env override, a comment in `wrangler.toml` **and a line in `.env.example`** (`npm run check:env` fails otherwise).
- **Avatar initials**: a display name often starts with an emoji, a decoration or a quote (`🌸 ana`, `«cita»`), so the fallback initial is the first **letter or number** of the display name, then of the username (`avatarInitial`, `lib/avatar.ts`). It iterates code points, so a surrogate pair is never cut in half (`👨‍👩‍👧 familia` → `F`); never take `display_name[0]`.
- **Images**: custom loader in `next.config.ts`; prefer `next/image`. For non-square remote avatars force `width`/`height` + `objectFit: "cover"` inline (Tailwind preflight overrides attributes).
- **Fonts**: Wix Madefor Text for UI/body and JetBrains Mono for code, both self-hosted via `next/font/google` (`app/layout.tsx`) with `subsets: ["latin", "latin-ext", "cyrillic"]` — the `ru` locale must not fall back to system-ui. Reference them through the `--font-sans` / `--font-mono` CSS variables (next/font hashes the family names at build time); never hardcode a family in components.
- **Remote content**: render via `renderRemoteContent`/helpers in `lib/activitypub/content.ts`; never inject raw remote HTML.
- **Objects**: set `updated_at = published` explicitly on insert (the column DEFAULT uses a different format and would mark new posts as edited).
- **ActivityStreams timestamps are ISO-8601** (`isoTimestamp`, `lib/activitypub/utils.ts`): SQLite's `datetime()` default writes `2026-08-07 12:51:03` (space, no zone). Ruby and JS parse that, the Rust `time` crate does not — it fails with "the 'offset hour' component could not be parsed", so an `aoderelay` relay cannot parse the actor document at all, errors out (`500 "Couldn't do the json thing"`) before even handling the `Follow`, and the subscription stays **pending forever** with no inbound activity to show for it. `buildActor`, `buildNote` and `applyPollToNote` normalize every timestamp they emit (an actor whose `published` came straight from `created_at` was the trigger); the DB format itself is left alone.
- **Media downloads are named after the resource, never the bucket**: cached media is served from `/api/media/<r2-key>`, so a bare `download` link saved `cache/media/<sha256>.jpg`. `mediaDownloadName` (`lib/media/filename.ts`) resolves the attachment's **description** (what the user wrote when publishing) with the served extension, then the file name their own upload kept in the key (`media/<user>/<uuid>-<name>`), then the R2 key basename; `MediaPlayer`'s download link and the lightbox/AP players pass it as the `download` attribute. The media cache, its R2 keys and the served URLs are untouched.
- **Tabs**: every tab bar (explore, timelines, notifications, lists, profiles, status detail) is `<Tabs>` from `components/Tabs.tsx` — sizing, font and the selected state live in the shared `.tab` class (`app/globals.css`, state via `aria-selected`); never hand-roll another one. `scroll` switches the row to auto-width tabs with horizontal overflow (profiles), otherwise tabs share the row equally.
- **Style**: no comments unless they explain *why*; TypeScript strict; `setX`/`handleX`/`fetchX` naming; admin pages keep the emoji prefix in nav/titles.

## Testing

- Two Vitest projects in `vitest.config.mts`: **`unit`** (jsdom, tests under `lib/**`: components, pure logic and route handlers with mocked bindings) and **`workers`** (`test/**/*.workers.test.ts`, running inside **workerd** via `@cloudflare/vitest-plugin` with the real bindings from `wrangler.toml` through Miniflare). `npx vitest run` runs both; `npm run test:unit` / `npm run test:workers` filter with `--project`.
- **Anything that touches D1/KV/R2 belongs in the `workers` project**: storage is isolated per test file, so `beforeAll(applyTestSchema())` applies `lib/db/schema.sql` once and `beforeEach(resetTestDatabase() / resetTestStorage())` gives every test a clean slate (`test/helpers/db.ts`). The schema is split by Wrangler's own SQL splitter in the config and injected as the `TEST_SCHEMA` binding.
- Workers tests import `env` from `cloudflare:workers` (typed via the `Cloudflare.Env` augmentation in `test/env.d.ts`); route handlers can be called directly — they read the test Worker's bindings through `cloudflare:workers` with no context shim. `test/worker.ts` is the test Worker entry (re-exports the DO classes) because `src/worker.ts` imports the vinext app handler; the assets directory is overridden so tests run on a fresh clone without a build. The workers project runs serially (`fileParallelism: false`) to avoid a pool-teardown race. AI/Vectorize bindings have no local simulator, so Miniflare prints a warning on every workers run — expected, tests never call them: `test/setup-workers.ts` mocks the Guardian's vector memory (`@/lib/moderation/vectors` and `@/lib/moderation/learn`, registered under both the alias and the relative specifier because the Cloudflare plugin's bundling keys them separately) for the whole project, since merely reading `env.VECTORIZE` raises the stub's rejection. A test file that needs the real shape overrides it with its own `vi.mock`.
- Unit tests that mock their module graph use `vi.mock` + `vi.hoisted` (federation `safeFetch`, `@/lib/streaming/broadcast`, `@/lib/push`); API-route unit tests mock the `cloudflare:workers` `env` — the jsdom project maps that specifier to `test/stubs/cloudflare-workers.ts` with a `resolveId` plugin (plain aliases lose to Vite's externalization), and tests do `vi.mock("cloudflare:workers", () => ({ get env() { return mocks.env; } }))` so bindings can be swapped per test — and the DB chain. Real behaviour (D1 constraints/cascades/triggers, R2 and KV) is covered in the workers project.
- When touching security, add tests: `lib/activitypub/__tests__/security.test.ts` (signatures, SSRF) and `queue.test.ts` (queue vs fallback). When touching call handling, seed the `call:<id>` KV session in the test context.

## Gotchas that have bitten before

- `wrangler.toml`'s `assets.directory` is the **build output** (`dist/client`) — the `.open-next/assets` of the OpenNext era no longer exists (the directory is absent, and only the Cloudflare Vite plugin's generated config masked it). `vite build` emits `dist/client` (static) + `dist/server` (the worker built from `src/worker.ts`) and writes `dist/server/wrangler.json` — the config `vinext-cloudflare deploy` actually ships — so keep the two in sync (`not_found_handling = "none"` keeps the worker answering every route instead of a static 404 page).

- `proxy.ts` (Next.js 16's renamed middleware convention; vinext accepts `proxy` or `default` exports) only imports `next/server` — it runs inside the same Worker as the app. No matcher means it covers every dynamic route (static assets are served by the Workers Assets layer before the Worker), and matcher patterns must survive vinext's safety parser: regexes with lookaheads are rejected.
- `src/worker.ts` is wrangler's `main`: wraps the vinext handler (`vinext/server/fetch-handler`), exports the DO classes, and adds the queue consumer (incl. DLQ), WebSocket upgrades for `/api/v1/streaming` and `/api/v1/calls/:id/ws`, and cron. Intercept those **before** `handler.fetch`.
- **Never reference DOM globals in Workers code** (`status`, `name`, `origin`, `top`, `event`…): with `lib.dom` in tsconfig TypeScript resolves them and `tsc` stays green, but at runtime in a Worker they throw (`ReferenceError`) — a surrounding `try/catch` can swallow it silently (a `status` typo made `broadcastObjectDelete` skip every list channel for months). Either fix, and prefer `obj.visibility`, never bare `status`.
- `serializeAccount.url` is the **human profile** for a remote account (`https://domain/@user`) and `uri` the ActivityPub id (Mastodon's semantics): the actor id answers JSON on most servers, so the remote badge and the "view original" button must open `url` or they land on a document instead of the profile.
- The geolocated status map (`LocationPreview`) is a tile mosaic **centred on the point**, so the card shows the window `[offsetX - w/2, offsetX + w/2]` of it: a point near the edge of its tile left a white strip on the right (41 px on a 645 px card, more on wider cards and on the oEmbed embed). The cover scale must be driven by the **frame's** size and by the pin-to-edge distances (`mapCoverScale`, `lib/location.ts`, unit-tested) — the original formula divided by the mosaic's own size, which is fixed, so it always resolved to 1 and never scaled.
- Cron phase drifts: `executeScheduled` aligns to the top of the minute; never assume `:00`.
- `getFollow` does **not** filter by state — use `isAcceptedFollower` for followers-only visibility.
- Removing local accounts must clean `oauth_tokens`, `activities` and `moderation_log` (no FKs) and federate a `Delete` tombstone (see `app/api/v1/accounts/delete/route.ts` and the admin DELETE route).
- Never re-ingest already-stored objects to change rendering — serializers read `objects.raw`, so rendering fixes are backward-compatible without migration.
- Web Push is silenced while a focused tab reports presence: the client heartbeats `POST /api/v1/push/presence` (D1 `push_subscriptions.present_until`, 120s — D1, not KV, so unfocusing is strongly consistent across colos) and `deliverPushNotification` skips while it is in the future. Do **not** instead skip `showNotification` in `public/sw.js` — Chrome substitutes "This site has been updated in the background" and burns the per-origin push budget.
